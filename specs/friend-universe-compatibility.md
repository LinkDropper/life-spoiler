## 개요

### 배경

"친구들과의 궁합 점수 보기"는 최근 SNS에서 반복적으로 바이럴되는 포맷이다(생일 기반 성향 테스트, 친구 관계 지도 등). 인생스포는 이미 자미두수 기반 1:1 유료 궁합(`app/compatibility/`)을 보유하고 있지만, 이는 로그인·프로필 생성·LLM 해석·구조화된 리포트가 필요한 무거운 플로우다. 반대로 "가볍게, 로그인 없이, 여러 명이 한 링크에 모여 별처럼 쌓이는" 형태의 참여형 콘텐츠는 없다.

이 기능은 무료·익명·초경량 진입 장벽으로 신규 유저 유입(바이럴 루프)을 만드는 것이 목적이며, 유료 전환은 화면 하단의 다른 운세 상품 홍보로 간접 연결한다.

### 목표

1. 링크 하나로 로그인 없이 "내 우주"를 만들고 친구를 초대할 수 있게 한다.
2. 친구가 참여할 때마다 자연스럽게 "나도 만들어볼까"로 이어지는 바이럴 루프를 닫는다(Phase 1 필수 조건).
3. 기존 유료 궁합/결제/엔타이틀먼트 파이프라인을 전혀 건드리지 않고 완전히 독립된 무료 기능으로 출시한다.

### 현재 구현 현황 (PRD 작성 시점 기준 — 병렬 진행 중)

이 PRD 작성과 병행해 CTO 산하 에이전트가 스키마/계산 엔진을 이미 착수했다. PRD는 이 실제 코드를 근거로 작성했으며, 아래 표의 항목은 "설계안"이 아니라 **이미 존재하는 코드**다.

| 영역 | 상태 | 근거 |
|---|---|---|
| DB 스키마 (`universes`, `universe_guests`) | 작성 완료 (원격 미적용, 사용자 승인 대기) | `supabase/migrations/005_create_friend_universe.sql` |
| 궁합 계산 엔진 (`calculateFriendCompatibility`) | 작성 완료, 성별 비의존성 테스트로 검증 | `libs/zi-wei-dou-shu/calculators/friend-compatibility.ts` |
| 결정론적 매트릭스 (`fu-1.0.0`) | 6개 축(띠/오행/명궁 자리/타고난 성향/친구 자리/사화 교차/천간) 작성 완료 | `libs/zi-wei-dou-shu/constants/friend-compatibility-table.ts` |
| Route Handler / 페이지 / 컴포넌트 / 훅 | **미착수** | `app/universe/**`, `app/api/universe/**` 없음 (2026-08-18 기준) |
| i18n 번역 키 | **미착수** | `messages/translations.json`에 `universe`/`friendUniverse` 키 없음 |

이 PRD의 실질적 역할은 (1) 이미 만들어진 스키마/엔진을 화면·플로우·정책 요구사항과 정합시키고, (2) 스키마에는 반영됐지만 초안 작성 시점에는 제품 정책으로 결정되지 않았던 것(개인정보 공개 범위, 어뷰징 하드캡 수치, 소유권 증명 사용 시점)을 CPO/CTO/사용자 협의를 거쳐 확정하고, (3) 계산 엔진 검증 중 발견된 실제 갭(시간 미상 처리)을 CTO에 정확히 전달해 확정받는 것이었다. 이 세 가지 모두 아래 각 절과 "결정 이력" 절에 확정 상태로 반영되어 있다(2026-08-18 기준 미결 항목 없음).

> **2026-08-19 추가 갱신**: 위 표는 2026-08-18 시점 스냅샷이며 이후 실제로 위 표의 "미착수" 항목까지 포함해 기능 전체가 구현되어 배포 전 QA에 들어갔다. QA 과정에서 이 PRD와 구현 사이의 불일치 2건이 발견돼 CPO가 아래와 같이 확정했다(신규 갭이므로 구현/스키마 추가 작업이 필요하다):
>
> 1. **owner 한줄평 미신설** — 섹션 1의 "owner 한줄평"이 실제로는 owner 개인 운세가 아니라 친구 유입 유도 문구로 구현되어 있었다(`universe.detail.ownerOneLiner` 번역키 확인됨). owner 1인 운세 한줄평을 신설하기로 확정 — "화면 구성 > 1. 최상단 — owner 요약" 절 참조.
> 2. **별 위치가 점수 순위에서 파생** — `libs/universe/star-visual.ts`의 `getStarPlacement`가 점수 내림차순 index로 동심원 위치를 결정론적으로 계산하고 있었다(위치가 저장되지 않고 매번 재계산됨). 등록 시점 랜덤 산출 후 영구 저장 방식으로 변경 확정 — "화면 구성 > 디자인 컨셉(우주 시각화) > 배치" 절 참조.

## 기존 기능과의 경계

| 항목 | 기존: 1:1 궁합 (`app/compatibility/`) | 신규: 친구 우주 궁합 (`app/universe/`) |
|---|---|---|
| 로그인 | 필요 (Supabase Auth) | **불필요** — 익명 링크만으로 식별 |
| 참여 인원 | 정확히 2명 (내 프로필 vs 상대 프로필) | 1명(owner) + N명(guest), 링크 하나에 다수 참여 |
| 프로필 저장 | `profiles` 테이블에 저장된 로그인 유저 프로필 사용 | `universes`/`universe_guests`에 별도 저장, `profiles`와 무관 |
| 결과 산출 | LLM(Gemini) 실시간 해석, 8개 인사이트 + 시나리오 + 조언 (수천 자) | **결정론적 사전 매트릭스 조회**, 점수+등급+한줄평+근거 factor 배열 (LLM 호출 없음) |
| 과금 | 유료 (결제 필요, `payment` 파이프라인 경유) | **완전 무료**, 결제/엔타이틀먼트 연동 없음 |
| `fortune_type` | `compatibility` (기존 `fortunes` 계열 테이블 사용) | **신규 `fortune_type` 발급하지 않음.** `universes`/`universe_guests`는 완전히 별도 테이블 |
| 공유 방식 | 결과 페이지 `share` 링크 (OG 메타 포함, 결과 스냅샷) | 우주 자체가 공유 링크의 단위 (`public_id`), 결과가 아니라 "장소"를 공유 |
| 데이터 모델 변경 범위 | 이번 기능에서 **일절 변경하지 않음** | 신규 테이블 2개만 추가 |

두 기능은 코드 경로, 데이터 모델, 과금 여부, 결과 산출 방식(LLM vs 결정론적 매트릭스) 전부가 다르다. 유일한 공통점은 "자미두수 기반 두 사람의 관계 분석"이라는 도메인 개념뿐이며, 계산 로직도 서로 다른 모듈(`calculators/compatibility.ts` vs `calculators/friend-compatibility.ts`)을 사용한다. 홈 화면에서는 기존 `CompatibilityFortuneCard`(유료 1:1 궁합)와 신규 카드가 나란히 노출되므로, 카드 카피에서 "무료/링크 공유형"이라는 톤을 명확히 구분해 유저가 두 기능을 혼동하지 않도록 한다(카피 확정은 marketer/designer 영역, 이 PRD는 구분 필요성만 명시).

## 사용자 시나리오

### 시나리오 A: 소유자가 처음 우주를 생성 → 링크 발급 → 공유

```
1. 유저가 홈 화면 최상단의 "친구 우주 궁합" 카드를 탭한다.
2. /universe/create 로 이동, 생년월일 + 태어난 시간(또는 "시간 모름") + 성별 + (선택) 표시 이름을 입력한다.
3. "우주 만들기" 제출 → POST /api/universe → universes 행 생성, public_id(nanoid 12자) 발급
4. 서버가 owner_token_hash용 원문 토큰을 HttpOnly 쿠키로 심는다 (향후 owner 전용 기능 대비, Phase 1 UI에서는 미사용)
5. /universe/{publicId}로 리다이렉트된다. 이 시점 "화면 구성" 절의 순서(6개 영역)대로 렌더링되며, 친구 별 0명 상태(빈 상태)를 본다.
6. 하단 "공유 링크 복사" 버튼으로 링크를 복사해 카카오톡/인스타 등으로 공유한다.
```

### 시나리오 B: 친구가 링크로 진입 → 이름+생년월일시 입력 → 자기 별이 우주에 추가되고 점수/한줄평 확인

```
1. 친구가 공유받은 /universe/{publicId} 링크를 연다.
2. 최상단에서 owner 요약(총 별 수, 한줄평)을 본다.
3. 2번째 영역의 입력 폼에 이름 + 생년월일 + 태어난 시간(또는 "시간 모름")을 입력한다 (성별 입력 없음).
4. "우주에 내 별 추가" 제출 → POST /api/universe/{publicId}/guests
   → 서버가 calculateFriendCompatibility(owner, guest)로 점수/한줄평/factors를 산출해 스냅샷 저장
5. 응답으로 본인의 점수/한줄평을 즉시 확인한다.
6. 3번째 우주 시각화에 자신의 별이 나타난다(30위 밖이어도 본인 별은 항상 개별 렌더링 — "디자인 컨셉(우주 시각화)" 절 참조).
7. 4번째 리스트에서 본인 항목이 하이라이트된 채로 스크롤된다.
8. 5번째 다른 운세 홍보, 6번째 공유 링크 복사를 보고 "나도 만들어볼까" 동선으로 이탈하거나 직접 우주를 생성한다(바이럴 루프 완결).
```

### 시나리오 C: 소유자가 나중에 자기 링크로 재방문 → 늘어난 친구 별들 확인

```
1. owner가 북마크/채팅방에 저장해둔 자기 링크를 다시 연다.
2. GET /api/universe/{publicId} → universes.guest_count, universe_guests 목록(점수 내림차순)을 조회한다.
3. 최상단 요약에 갱신된 친구 수/한줄평을 본다.
4. 3번째 시각화에서 늘어난 별들을 확인하고, 4번째 리스트를 스크롤해 각 친구의 점수/한줄평을 본다.
5. (last_viewed_at은 직전 갱신 후 1시간 경과 시에만 갱신 — 쓰기 증폭 방지, 마이그레이션 주석 반영)
```

### 엣지 플로우

#### E1. 친구가 링크로 들어왔는데 이미 입력한 적 있는 경우

- `idx_universe_guests_dedupe` 유니크 인덱스(우주+정규화 이름+생년월일시+역법+윤달 조합)가 이미 DB 레벨에서 존재를 보장한다.
- **정책**: 에러로 막지 않고 **upsert**로 처리한다. 동일 조합 재제출 시 새 행을 만들지 않고 기존 행의 점수/factors/calculated_at을 최신 매트릭스 버전 기준으로 갱신한다(단, `FRIEND_COMPATIBILITY_MATRIX_VERSION`이 바뀌지 않았다면 결과는 항상 같으므로 사실상 조회와 동일하게 동작).
- UX: "이미 참여한 별이에요!"라는 안내와 함께 기존 점수/한줄평을 그대로 보여주고, 3번째 시각화에서 본인 별로 스크롤+하이라이트한다(신규 등록과 동일한 결과 화면 재사용).
- 이름을 다르게 써서 같은 생년월일시로 재입력하는 경우는 인덱스가 이름까지 포함하므로 **막히지 않는다** — 별도 인물(동명이인 반대 케이스)로 간주하는 것이 의도된 설계다. 이는 어뷰징(같은 사람이 여러 별로 도배)을 완전히 막지 못하므로 아래 "어뷰징 방지" 절의 IP 쿨다운과 함께 방어한다.

#### E2. 소유자가 링크를 분실한 경우

- 로그인이 없으므로 서버가 "이 유저의 우주"를 능동적으로 찾아줄 방법이 없다(이메일/전화 등 식별자 미수집).
- **Phase 1 대응**: 없음 — 링크 분실 시 복구 불가. 생성 완료 화면(시나리오 A 5단계)에서 "이 링크는 다시 찾을 수 없어요, 꼭 저장/공유해두세요" 안내를 강하게 노출하는 것으로 예방한다(UX 안내, 기능적 복구 아님).
- **Phase 2 이후 검토**: 로그인 유저가 생성한 경우에 한해 `profiles` 또는 `auth.users`와 약한 연결(옵트인)을 저장해 "내 우주 목록" 조회를 제공하는 방안. 단 이는 "완전 익명"이라는 컨셉과 충돌하므로 옵트인이어야 하고, 이번 스코프의 확정 제약(익명 링크 기반)을 넘어서므로 반드시 별도 논의를 거친다. 이 PRD의 범위에는 포함하지 않는다.

#### E3. 친구 별이 0명일 때의 빈 상태(empty state)

> ⚠️ **2026-08-19 CPO 결정으로 갱신.** 1번째 영역 문구 처리 방식이 바뀌었다. 아래 세 번째 항목 참조 — 나머지 항목은 변경 없음.

- 3번째 시각화 영역: 중앙 owner 별만 표시, 링 1/2는 비어 있음. 배경 성운 그라디언트는 그대로 유지. (변경 없음)
- 4번째 리스트 영역: "아직 참여한 친구가 없어요. 링크를 공유해서 첫 번째 별을 초대해보세요" 안내 + 공유 버튼 단축 진입(6번째 영역과 동일 동작을 여기서도 노출). (변경 없음)
- 1번째 owner 요약: **"총 별 수"는 0으로 표시하고, owner 운세 한줄평은 친구 0명이어도 그대로 노출된다** — owner 1인 차트만으로 산출되므로 친구 유무와 무관하다(위 "1. 최상단 — owner 요약" 절 참조). **현행 구현의 "우주가 열렸어요. 이제 친구들을 초대해 별을 채워보세요"(`ownerEmptyOneLiner`) 같은 초대 유도 톤 문구는 섹션 1에서 제거하고 섹션 6(공유 링크 복사)으로 재배치한다.** 빈 우주에서 최상단이 허전해지는 문제도 owner 한줄평이 항상 노출됨으로써 동시에 해결된다.

#### E4. (추가) owner가 자기 링크에서 스스로 친구 입력 폼을 작성하는 경우

- 로그인이 없어 서버가 현재 방문자가 owner인지 friend인지 구분하지 못하므로, owner도 동일한 페이지에서 친구 입력 폼을 볼 수 있고 막을 이유가 없다.
- owner가 자신의 정보로(또는 임의 이름으로) 폼을 채워도 정상적인 `universe_guests` 행으로 처리한다. 악용(자기 자신을 여러 개 등록해 우주를 부풀리는 것)은 아래 "어뷰징 방지" 절 정책으로 제한한다.

#### E5. 계산 엔진 에러 (자미두수 계산 실패)

- `calculateFriendCompatibility`는 내부적으로 `ZiWeiError`를 던질 수 있다(예: 잘못된 시진 값). 입력 폼의 클라이언트 검증으로 대부분 방지되지만, 서버에서도 반드시 재검증한다.
- 계산 실패 시 `universe_guests` 행을 생성하지 않고 사용자에게 "입력값을 다시 확인해주세요" 인라인 에러를 반환한다(에러 처리 규칙에 따라 근본 원인 없이 기본값으로 채우지 않는다).

### 1. 최상단 — owner 요약

> ⚠️ **2026-08-19 CPO 결정으로 신규 기능 추가.** 아래는 이 절의 확정 사양이며, 현재 구현과의 차이는 바로 아래 "현행 → 변경 대조" 표로 정리했다.

**배경**: 사용자 최초 요청 원문은 "최상단에는 이 링크의 주인인 나에 대한 **운세**를 매우 간략하게 보여줍니다. 총 별자리의 수와 **운세에 대한 한줄평**등을 보여줍니다"였다. 여기서 "한줄평"은 owner 본인의 운세 한줄평을 뜻했다. 그런데 초기 PRD 작성 과정에서 "owner 한줄평"이라는 용어만 남고 실제 의미가 "친구 유입 유도 문구"로 바뀌었고, 구현도 그렇게 나갔다(현재 `universe.detail.ownerOneLiner` 번역키 = `"{count}명의 친구가 이 우주에 별로 떠 있어요."` — owner 개인 운세가 아니라 친구 수 기반 유도 카피다). 요구사항 미충족으로 판단해 **owner 개인의 운세 한줄평을 실제로 신설**한다.

**현행 → 변경 대조**

| 항목 | 현행 구현 | 변경 (확정) |
|---|---|---|
| 섹션 1 구성 | owner 타이틀 + 별 수 + (친구 유입 유도 문구, "owner 한줄평"이라는 이름으로 오용) | owner 타이틀 + 별 수 + **owner 운세 한줄평(신규, 실제 owner 1인 운세)** |
| 문구 산출 근거 | `guestCount`(친구 수) | **owner 1인 명반**(생년월일시)만으로 산출, 친구 수/친구 데이터와 무관 |
| 문구 조회 테이블 | `FRIEND_ONE_LINERS`(친구 궁합 매트릭스, `oneLinerId` 키) | **별도 신설 결정론적 테이블**(가칭 `OWNER_ONE_LINERS`) — 친구 궁합 매트릭스와는 다른 테이블이다. 상대가 없는 1인 운세라 판정 축 자체가 다르다. 구체 축 설계는 ziwei-expert 산출물, 이 PRD는 계약 조건만 명시(아래 "자미두수 매트릭스 연동 인터페이스 > owner 한줄평 테이블" 절 참조) |
| 기존 `ownerOneLiner` 카피(친구 유입 유도)의 위치 | 섹션 1 | **섹션 6(공유 링크 복사)으로 이관** — 아래 "6. 공유 링크 복사" 절 참조. 유도 카피는 그 행동을 할 수단이 있는 자리(공유 버튼 옆)에 두는 것이 맞다 |
| 친구 0명(E3)일 때 최상단 문구 | `ownerEmptyOneLiner`("우주가 열렸어요. 이제 친구들을 초대해 별을 채워보세요" — 친구 초대 유도 톤) | **owner 운세 한줄평이 그대로 노출**된다(1인 차트 기반이라 친구 0명이어도 산출 가능). 친구 초대 유도 문구는 섹션 6/별 수 자리로 재배치 — 아래 "E3" 절 참조 |

**필수 요소 (변경 후)**: owner 표시 이름(선택 입력값, 없으면 중립 문구) / 총 친구(별) 수 / **owner 운세 한줄평(신규, 친구 수와 무관하게 항상 노출)**
**상태**: 로딩(스켈레톤) / 에러(우주 없음 — 아래 참조) / 정상 — 변경 없음
**액션**: 없음(읽기 전용) — 변경 없음

**owner 한줄평 계약 조건 (확정)**

- **LLM 실시간 생성 금지** (이 기능 전체의 확정 제약과 동일 — "제약사항" 절 참조).
- **날짜 의존 금지.** "오늘의 운세"처럼 날짜에 따라 바뀌는 축을 쓰지 않는다. 근거: 이 화면은 링크로 공유되고 스크린샷으로 유통된다. 어제 캡처한 화면과 오늘 들어온 친구가 보는 화면이 다르면 공유 콘텐츠로서 신뢰가 깨지고, 캐시 무효화 인프라도 새로 필요해진다. owner 차트에서만 파생되는 **불변** 한줄평으로 간다.
- **테이블 규모**: 서로 다른 결과 **최소 50가지 이상**(15가지 수준이면 확산 시 같은 문구가 반복돼 템플릿 티가 난다).
- **문구 규격**: 45자 이내 / 존댓말 / **자미두수 전문 용어를 문구 표면에 노출 금지**(링크로 처음 들어온 사람이 읽는 최상단 헤드라인이므로) / 의료·법률·투자 조언으로 오해되는 표현 금지 / 적중률 주장 금지.
- **검수 기준**: 한 화면에 1개만 노출되므로 리스트 동시 노출 문제는 없다. 대신 **여러 사용자의 스크린샷이 나란히 놓였을 때 다양해 보이는가**로 판정한다.
- **저장 방식**: 슬러그(id)만 저장, 문구 원문은 조회 시점 해석. `libs/universe/one-liner.ts`의 append-only 슬러그 계약 패턴(스냅샷에는 id만 저장하고 문구는 조회 시 사전에서 조회 — 오타 수정/번역 확장이 과거 데이터에도 소급 반영되도록)을 그대로 따른다. i18n은 기존 정책대로 KO 우선(EN/JA는 Phase 2, "(c) i18n 출시 정책" 절과 동일 원칙).
- **유료 상품 잠식 방지**: 무료 바이럴 기능이므로 딱 한 줄 티저여야 한다. 상세 해석·복수 문장·항목별 운세 금지. 섹션 5(다른 운세 홍보)로 이어지는 도입 역할만 한다.
- **친구 0명(E3)일 때도 owner 한줄평은 그대로 노출**한다. 1인 차트 기반이라 친구가 없어도 산출되며, 빈 우주에서 최상단이 허전해지는 문제가 동시에 해결된다. 빈 상태 안내 문구는 별 수 자리 또는 섹션 6으로 재배치.
- **owner 이름 미입력(`ownerName === null`)이어도 한줄평은 노출된다** — 생년월일시는 필수 입력이므로 산출 가능.
- **개인정보 경계**: 응답 DTO에는 슬러그/문구만 담기고 원본 생년월일시나 명반 구조는 나가지 않는다(`libs/universe/types.ts`의 `PersonalDataKey` 컴파일 타임 가드 유지 — 신규 필드 추가 시에도 이 가드를 통과해야 한다). 문구가 생시를 역산 가능하게 특정해서도 안 된다(예: "새벽에 태어난 분들은…" 류 금지).
- **산출 시점**: 우주 생성 시점(owner 생성 폼 제출 시)에 슬러그를 산출해 DB에 저장하는 방식을 프로덕트 선호로 명시한다. 다만 최종 기술 판단(생성 시 저장 vs 조회 시 지연 계산)은 CTO 소관이다.
- **owner가 시간 미상(`estimated`)인 경우**: 시간에 의존하지 않는 축만으로도 산출 가능한 폴백이 필요하다. 단, 이 우주는 이미 estimated 배너를 1회 노출하므로("디자인 컨셉 > `estimated` 상태 표시" 절 참조) 한줄평에 별도 고지를 중복해 붙이지 않는다.

세부 슬러그 개수·조회 계약은 아래 "자미두수 매트릭스 연동 인터페이스 > owner 한줄평 테이블 (신규 계약)" 절 참조.

### 2. 친구 입력 폼

- **필수 요소**: 이름(1~20자, 필수) / 생년월일(필수) / 태어난 시간 또는 "시간 모름" 체크박스(`app/profile/setup/StepOne.tsx`의 기존 UX 패턴 재사용 권장) / 양력·음력·윤달 선택 / "우주에 내 별 추가" 버튼
- **성별 입력 없음** (owner와 달리 friend는 성별을 받지 않음 — 컨셉 확정 사항)
- **상태**: 입력 중(인라인 검증) / 제출 중(버튼 비활성+로딩) / 성공(결과 즉시 표시 + 3번째 영역으로 자기 별 강조) / 실패(에러 메시지, 폼 값 유지)
- **액션**: 제출, 이미 등록된 조합이면 E1 정책대로 처리

### 3. 우주 시각화

- 아래 "디자인 컨셉(우주 시각화)" 절을 그대로 따른다(치수/애니메이션/접근성 요구사항은 해당 절에 통합 기재, 여기서는 화면상 위치와 상태만 정의).
- **상태**: 별 0개(E3 빈 상태) / 1~30명(전원 개별 렌더링) / 31명 이상(+N 클러스터 배지 노출) / 방금 등록한 본인 별이 30위 밖이어도 항상 강조 렌더링(CPO 결정)
- **액션**: 별 탭 → 4번째 리스트 해당 행으로 스크롤 + 하이라이트, 스킵 링크 → 4번째 리스트로 즉시 이동

### 4. 궁합 점수·한줄평 리스트

- **필수 요소**: 점수 내림차순 정렬된 `<ol>`. 각 행에 순위, 이름, 점수, **등급(tier) 라벨**, 한줄평. 접근성 대체 구조로서 시각화보다 항상 완전한 정보를 제공한다(아래 "디자인 컨셉(우주 시각화)" 절 a11y 요구사항 참조, tier 체계는 "자미두수 매트릭스 연동 인터페이스" 절의 등급 표 참조).
- **상태**: 빈 상태(E3) / 목록 있음. 페이지네이션 없음(Phase 1은 전원 노출, 성능 이슈 발생 시 Phase 2에서 가상 스크롤/페이지네이션 검토)
- **액션**: 방금 등록한 본인 행 자동 하이라이트(1.2초 펄스, 3번째 영역과 동일 트리거 공유)

### 5. 다른 운세 홍보 버튼

- **필수 요소**: 평생운세/올해운세/내년운세/궁합(유료 1:1) 4개 카드 또는 배너. 각 버튼은 `/profiles?type=...` 또는 `/compatibility`로 연결(기존 라우팅 재사용, 신규 라우팅 불필요)
- **상태**: 정적 노출(로딩/에러 없음)
- **액션**: 탭 시 각 상품 진입 플로우로 이동 — 로그인 안 되어 있으면 기존 로그인 플로우가 자연히 개입(이 기능만 익명이고, 다른 상품은 기존과 동일하게 로그인 필요)

### 6. 공유 링크 복사

> ⚠️ **2026-08-19 CPO 결정으로 갱신.** 기존 섹션 1에 있던 친구 유입 유도 문구(`ownerOneLiner`, "{count}명의 친구가 이 우주에 별로 떠 있어요" 계열)를 이 섹션으로 이관했다. 근거: 유도 카피는 그 행동을 할 수단이 있는 자리에 둔다 — 공유 버튼 옆이 정확히 그 자리다. 섹션 1은 owner 운세 한줄평으로 대체됐다(위 "1. 최상단 — owner 요약" 절 참조).

- **필수 요소**: `https://life-spoiler.com/universe/{publicId}` 복사 버튼 + **친구 유입 유도 문구(이관된 위치, 기존 `ownerOneLiner`/`ownerEmptyOneLiner` 카피를 이 섹션 문맥에 맞게 재사용)**(UTM은 웹→웹 내부 공유이므로 필수 아님, 단 카카오톡 공유 시트 등 외부 채널 연동 시 `.claude/rules/utm-parameters.md` 기준 준수 검토는 marketer 영역)
- **상태**: 복사 성공 토스트 / 클립보드 API 미지원 브라우저 폴백(수동 선택 안내)

## 디자인 컨셉 (우주 시각화)

designer 산출, CPO 승인 완료. 3번째 영역("우주 시각화")에 그대로 적용한다. 수치는 원안을 그대로 옮겼다.

### 기술 스택

신규 의존성 없이 **DOM `<button>` + CSS**로 구현한다. SVG/Canvas/WebGL은 모두 기각(접근성·번들 사이즈 근거). 애니메이션은 `transform`/`opacity`/`filter`만 사용한다.

### 점수 → 시각 매핑 (확정)

디자이너 재보정 완료, CPO 승인(2026-08-18). 정의역은 이론적 0~100이 아니라 **`FRIEND_COMPATIBILITY_MIN_SCORE`(12)~`FRIEND_COMPATIBILITY_MAX_SCORE`(99)** — 이 상수를 코드에서 그대로 import해서 사용하며, `12`/`99`를 별도로 하드코딩하지 않는다(실제 clamp 경계와 항상 동기화되도록 하기 위함). 이징 지수는 `1.4` → **`1.6`**으로 조정했다(주요 tier 경계 사이 직경차가 3px 이상 확보되는 최소값 — 2.2까지 올리면 bright-orbit과 twin-star 구간이 오히려 수렴해 역효과가 난다). 직경 상한은 `30px` → **`32px`**로 조정했다(소유자 별 44px 대비 27% 작아 위계는 유지된다).

**이 정의역 `[12, 99]`는 `confidence`("(b) 태어난 시간을 모르는 사용자 처리" 절 참조) 값과 무관하게 항상 고정이다 (CPO 결정).** `estimated`(시간 미상) 우주는 점수 폭이 더 좁게 나오지만, 그렇다고 우주별로 정의역을 좁히면 같은 70점이 우주마다 다른 크기로 보여 사용자 간 스크린샷 비교가 깨진다.

```ts
const SCORE_DOMAIN_MIN = 12; // FRIEND_COMPATIBILITY_MIN_SCORE
const SCORE_DOMAIN_MAX = 99; // FRIEND_COMPATIBILITY_MAX_SCORE
const EASE_EXPONENT = 1.6;

function getStarVisual(score: number) {
  const clamped = clamp(score, SCORE_DOMAIN_MIN, SCORE_DOMAIN_MAX);
  const t = (clamped - SCORE_DOMAIN_MIN) / (SCORE_DOMAIN_MAX - SCORE_DOMAIN_MIN);
  const eased = Math.pow(t, EASE_EXPONENT);
  return {
    diameterPx: Math.round(10 + 22 * eased),        // 10~32px
    coreOpacity: +(0.55 + 0.45 * eased).toFixed(2), // 0.55~1.0
    glowBlurPx: Math.round(4 + 16 * eased),         // 4~20px
    glowSpreadPx: Math.round(0 + 4 * eased),        // 0~4px
    glowAlpha: +(0.25 + 0.45 * eased).toFixed(2),   // 0.25~0.70
  };
}
```

소유자 별은 이 매핑과 무관하게 고정값을 쓴다: 직경 44px / opacity 1 / glowBlur 28px / glowSpread 4px / glowAlpha 0.6.

| 41 | 먼 별(상한) | 13.8px | 0.63 | 7px | 1px | 0.33 |

### tier 사용 방식 (확정)

**시각 크기/밝기는 위 공식으로 연속 매핑하고, tier(6단계)는 크기에 스냅하지 않는다 — 텍스트 채널로만 이산적으로 노출한다.** 6단계로 크기까지 스냅하지 않는 이유:

- 별 20~30개가 6종류 크기로만 보이면 "각자 다른 사람"이라는 컨셉 자체가 죽는다(연속 매핑이라야 30개가 30가지로 보인다).
- tier 경계에서 1점 차이(예: 65→66)로 크기가 계단식으로 튀면 부자연스럽고, 근소한 점수 차이가 실제보다 과장돼 보인다.
- 접근성 요구사항(궁합 순위를 시각 정보 외 채널로 전달)은 시각 크기가 아니라 **텍스트 라벨만으로 이미 충족된다** — tier 라벨이 그 채널이다.

**텍스트 노출 포맷 (확정)**

- 별 `aria-label`: `"{name}, 궁합 점수 {score}점, {tier.labelKo}, 전체 {total}명 중 {rank}위"` (예: "지민, 궁합 점수 82점, 밝은 궤도, 전체 12명 중 3위"). 본인 별은 접두사 `"(나) "`를 붙인다(아래 "본인 별 강조 방식" 참조).
- 4번째 리스트 행: `"{rank}위 · {name} · {tier.labelKo} · 궁합 {score}점 — {oneLiner}"`
- `FRIEND_COMPATIBILITY_TIERS`(등급 구간/라벨)는 UI에서 재정의하지 않고 `libs/zi-wei-dou-shu/constants/friend-compatibility-table.ts`에서 그대로 import한다(단일 소스 유지, tier 슬러그·라벨·경계값이 두 곳에 따로 존재하지 않도록).

### 본인 별 강조 방식 (확정)

**본인 별의 크기/밝기를 실제 점수보다 부풀리는 방식은 금지한다.** 본인 점수가 낮으면 본인 별도 위 매핑대로 정직하게 작고 어둡게 나온다 — 점수를 속여 크게 보이게 하면 "궁합 점수가 곧 서사"라는 이 기능의 신뢰가 깨진다. 대신 크기와 무관한 **별도 레이어**로 식별시킨다:

- 흰색 outline 링: `outline: 1.5px solid rgba(255,255,255,0.9); outline-offset: 3px` (별 자체 glow와 분리된 레이어)
- 최초 진입 시 1회성 arrival pulse 애니메이션(`prefers-reduced-motion: reduce`에서는 생략)
- `aria-label` 앞에 `"(나) "` 접두 (위 텍스트 노출 포맷 참조)

"30위 밖이어도 항상 개별 렌더링"이라는 CPO 결정(아래 "배치" 절)은 유지되며, 이 절은 그 개별 렌더링된 본인 별을 **어떻게** 식별시키는지(크기 왜곡이 아니라 outline/pulse/aria-label)에 대한 것이다.

### `estimated` 상태 표시 (확정, designer 산출·CPO 승인)

"(b) 태어난 시간을 모르는 사용자 처리" 절에서 확정된 `confidence: "exact" | "estimated"`를 시각화에 어떻게 드러낼지에 대한 절이다. **핵심 원칙: 표시 단위를 노출 범위와 일치시킨다.** 두 케이스는 상호 배타적이다(owner가 estimated면 그 우주의 모든 쌍이 이미 그 하위집합이므로 개별 guest에 중복 표시할 필요가 없다).

| 케이스 | 범위 | 노출 |
|---|---|---|
| owner 시간 미상 (우주 전체 estimated) | 이 우주의 모든 쌍 | 1번째 영역(owner 요약)에 배너 1개 + 3번째 영역(시각화) 캔버스 **위 헤더 캡션** 1줄. **개별 별/리스트 행에는 표시하지 않는다** |
| owner는 exact, 특정 guest만 시간 미상 | 그 guest 1명 | 4번째 리스트의 해당 행에만 작은 태그 칩. 배너 없음 |

별 30개에 같은 태그가 전부 붙으면 정보가 아니라 벽지가 되므로, 우주 전체가 `estimated`인 경우 개별 별·리스트 행에 반복 표시하지 않는다.

**별 자체에는 estimated 표식을 주지 않는다.** 10~32px 안에 이미 점수 기반 크기/glow, twinkle/float 애니메이션, "본인 별" 흰색 outline 링까지 3개 시각 채널이 쌓여 있어, 4번째 채널을 얹으면 이 크기에서 신뢰성 있게 구분되지 않고 특히 "본인 별" outline 링과 충돌한다. 우주 전체 estimated는 위 배너로 이미 고지되고, 남는 케이스는 "guest 1명만 estimated"라는 드문 예외뿐이라 캔버스에 상설 채널을 추가할 실익이 없다.

3번째 영역 캔버스 **위 헤더 영역**(별밭 내부가 아님) 캡션은 "왜 별이 다 작지?"라는 혼란이 실제로 발생하는 지점이라 원인 설명이 가장 필요한 자리다. 별밭 내부에 배지/아이콘을 넣는 것이 아니라 진입 전 텍스트 한 줄이므로 6개 영역 구조를 깨지 않는다.

**aria-label 규칙**: "고지 대상이 화면 전체면 개별 label에서 빼고 region 레벨에서 1회 고지, 고지 대상이 별 1개면 그 별 label에 포함."
- 우주 전체 estimated: 개별 별 `aria-label`은 위 "tier 사용 방식" 절의 기존 포맷 그대로 유지한다. 대신 3번째 영역 컨테이너의 `aria-label`에 1회 고지한다 — `"{ownerName}님의 우주. 태어난 시간이 확인되지 않아 이 우주의 궁합 결과는 평균값으로 계산됩니다."`(스크린리더가 별밭 진입 시 한 번만 듣고, 30개 별을 순회할 때는 반복 없이 랭킹 정보만 듣는다)
- guest 1명만 estimated: 그 별의 `aria-label`에만 추가한다 — `"{name}, 궁합 점수 {score}점, {tier.labelKo}, 전체 {total}명 중 {rank}위, 태어난 시간 미상으로 평균 계산됨"`

**행 태그 칩**: `components/compatibility/CompatibilityCard.module.css`의 기존 `.tag` 칩 스타일을 그대로 재사용한다(신규 시각 언어 없음). 칩 텍스트는 **"예상치" / "Estimated" / "推定値"** 로 확정 — "미상/불명" 계열은 결핍처럼 읽혀 브랜드 톤과 어긋나므로 금지한다.

**다국어 처리는 문구 종류에 따라 반대 원칙을 적용한다**:
- **배너/캡션(설명 문장)**: 줄바꿈을 허용하고 `nowrap`/말줄임을 **금지**한다. 설명 문장은 잘리면 안 된다 — 위 "다국어/긴 이름" 절의 별 이름 라벨 말줄임 원칙과 **정반대**라는 점에 유의한다. EN/JA는 2줄까지 자연스럽게 감싼다.
- **행 태그 칩(짧은 상태 라벨)**: 좁은 뷰포트에서 이름+점수+칩이 한 줄에 안 들어가면 `.infoRow`가 `flex-wrap`으로 칩만 다음 줄로 넘긴다(잘림/생략 금지 — 부가정보라 줄바꿈 비용이 낮다).

> **카피 의도(향후 수정자를 위한 근거)**: 두 문구 모두 "미상/불확실/정확도" 계열 단어와 행동 유도 어휘("넣으면", "~해보세요")를 의도적으로 배제했다. "차분하게 / softly / やわらかく"는 평균화로 밝기가 낮아진 별을 **결함이 아니라 이 우주만의 톤**으로 재해석하는 것이 핵심 의도다 — 이 프레이밍을 유지한 채로만 문구를 수정한다.

**Phase 1에는 CTA를 넣지 않는다.** owner가 우주 생성 후 시간을 재입력할 경로가 Phase 1에 없다 — owner 전용 액션은 `owner_token_hash` 검증이 전제인데, 그 검증 자체가 "소유권 증명 메커니즘" 절에서 확정했듯 Phase 2다(Phase 1은 쿠키 발급만 하고 검증하지 않는다). 따라서:
- Phase 1 배너/캡션은 **설명형이며 CTA를 붙이지 않는다.** 넣을 방법이 없는데 넣으라고 하면 막다른 배너가 되어 없는 것보다 나쁘다. "부정형 금지"(결핍이 아니라 계산 방식의 차이로 읽히게) 원칙은 유지한다.
- **설득/유도는 owner 생성 폼 시점으로 옮긴다** — 이는 이미 "(b) 태어난 시간을 모르는 사용자 처리" 절의 owner 생성 폼 안내("시간을 넣으면 친구들 결과가 더 뚜렷하게 갈려요")와 동일 지점이다. 애초에 `estimated` 우주가 덜 생기게 하는 것이 사후 배너보다 효과적이고, 이 시점에는 실제로 입력할 수단이 있다.
- **Phase 2 체크리스트 추가 항목**: owner 토큰 검증 도입 시 "owner 시간 재입력 경로 + estimated 배너 CTA + 뷰어(owner/guest) 분기"를 함께 넣는다. guest는 owner 데이터를 고칠 권한이 없으므로 guest 뷰에는 같은 CTA를 노출하지 않는다.

#### 폐기된 규칙 (현행 구현, `libs/universe/star-visual.ts`의 `getStarPlacement`)

동심원 2개 링. ring1 반경 20%(용량 12명), ring2 반경 30%(용량 18명) → 개별 렌더링 상한 30명. **점수 내림차순 index로 안쪽 링부터 채운다(1등이 소유자와 가장 가까움).** 각도에는 `star_seed` 기반 결정적 지터를 적용한다. 31명 이상은 외곽에 `+N` 클러스터 배지 1개로 표시.

#### 폐기 근거 (CPO 확정)

1. 사용자 최초 요청에 있던 규칙은 "궁합이 높을수록 크기가 크고 밝기가 밝다" 뿐이었다. **위치 규칙은 사용자 요구가 아니라 PRD 작성 단계에서 추가된 파생 규칙**이었다.
2. 거리는 순위의 **중복 채널**이었다. 순위는 크기·밝기·섹션 4 리스트에서 이미 3중으로 전달되므로 거리 채널을 빼도 정보 손실이 없다.
3. 반대로 현 방식에는 실사용 결함이 있다: 위치가 "현재 전체 목록의 점수 순위"에서 파생되므로 **새 친구가 높은 점수로 들어오면 기존 별들이 밀려난다.** 재방문한 사용자에게 "내 별이 어디 갔지"가 발생하고, 이는 재공유 동기를 직접 깎는다.
4. 따라서 **크기/밝기 = 점수 기반(유지), 위치 = 점수와 무관한 등록 시점 랜덤 + 영구 저장(변경)**으로 두 축을 분리한다. 사용자 최초 요청과 충돌하지 않는다.

#### 신규 확정 규칙

- 위치는 **등록 시점에 랜덤 산출 후 DB에 영구 저장**한다. 한 번 정해진 위치는 다른 친구가 새로 등록되든, 점수가 어떻든, 재조회하든 **절대 변하지 않는다.** 이것이 이 변경의 목적 전부다.
- 이 랜덤은 **등록 시점에 서버에서 1회만 실행되고 결과가 DB에 저장**된다. 클라이언트 렌더마다 반복 실행되는 `Math.random()`과는 성격이 다르므로, 기존 "`Math.random()` 금지"(SSR/CSR hydration mismatch 방지) 원칙과 충돌하지 않는다 — 애니메이션 위상의 결정론 규칙은 아래 그대로 유지된다.
- 저장 포맷은 **비율**(각도+반경비 또는 x/y 비율)이어야 하고 **절대 px는 금지**한다(컨테이너 크기가 바뀌어도 상대 위치가 유지되어야 하므로). 정확한 컬럼 스키마는 CTO 소관이며 **마이그레이션 006**이 필요하다(아래 "데이터 요구사항 > 스키마" 절 참조).
- **겹침 방지**: 완전 균일 랜덤은 겹친다. "랜덤이되 최소 간격 보장"(후보 좌표 추첨 → 기존 좌표와 최소 거리 미달이면 재추첨 → N회 실패 시 폴백 슬롯) 방식이 필요하다. 기존 겹침 회귀 테스트 3개(`libs/universe/__tests__/star-visual.test.ts` 소재)는 랜덤 배치 방식에서도 통과해야 한다.
- **최소 간격 판정은 별 직경(코어 반지름) 기준으로만 한다. 이름 라벨 pill 폭은 별끼리의 간격 판정에 넣지 않는다.**

  ⚠️ **이건 누락이 아니라 의도된 배제다. 되돌리지 말 것.** CPO가 처음에는 "라벨 폭도 반영"을 요구했다가 다음 근거로 **철회**했다(2026-08-19): 라벨 폭(68px)까지 안 겹치게 배치할 수 있는 이론 상한이 12~20명인데, 이는 **개별 렌더링 상한 30명과 물리적으로 양립 불가**다. 라벨 폭을 판정에 넣으면 배치 가능 인원이 반토막 난다.

  라벨 폭은 **캔버스 이탈 방지 마진에만** 사용한다(별이 화면 밖으로 나가 라벨이 잘리는 것은 막되, 라벨끼리 겹치는 것은 판정하지 않는다). 기존 회귀 테스트가 쓰던 기준과 동일하다.

  라벨 겹침 자체는 **랜덤 배치 도입과 무관하게 현행 링 배치에서도 이미 발생 중인 별개 문제**이며, 배치 알고리즘이 아니라 표시 정책으로 풀어야 한다 → "구현 단계 > Phase 2 > 이름 라벨 표시 정책 재설계" 항목 참조.
- **오너 별은 중앙 고정**(변경 없음). 오너 별 주변에 친구 별이 들어오지 않는 **금지 반경**을 둬야 한다.
- **개별 렌더링 상한 30명 + 31명 이상 `+N` 배지는 유지**(성능·겹침 방지 목적은 동일). 다만 위치가 점수와 무관해졌으므로 렌더 대상 30명 선정 기준이 별도로 필요하다 → **확정: 점수 상위 30명(현행 유지).**

  ⚠️ **"등록 순(선착순) 30명"으로 가자는 안이 검토 과정에서 나왔다가 기각됐다. 되돌리지 말 것.** 선착순 안의 근거였던 "위치를 영구 저장해놓고 렌더 대상만 점수순으로 고르면 어제 보이던 내 별이 오늘 사라진다"는 다음 세 가지로 반박되어 CPO가 스스로 **철회**했고, 팀 리더도 점수 상위 30으로 최종 확정했다(2026-08-19):

  1. **점수는 등록 시점 스냅샷으로 고정되고 이후 재계산되지 않는다.** 순위 밀림이 단조하며, (a) 우주에 이미 30명 이상 + (b) 그보다 높은 점수의 친구가 새로 진입, 두 조건이 겹칠 때만 발생한다. 상시 요동치는 것이 아니다.
  2. **30명 미만 우주에서는 두 안이 완전히 동일하다.** 대부분의 우주가 이 구간이므로, 선택은 "30명을 넘긴 큰 우주에서 어느 쪽이 나은가"로 좁혀진다. 그리고 큰 우주는 이 기능이 가장 잘 작동한 우주이자 가장 많이 공유될 우주다 — 거기서 시각화가 "궁합 좋은 친구들"이 아니라 "먼저 온 30명"을 보여주면 owner의 공유 자산이 망가진다.
  3. **손실이 비대칭이다.** 재방문한 guest에게는 Phase 1에서 본인 별을 식별할 수단이 없으므로(본인 강조는 방금 등록한 세션에만 걸린다) "내 별이 사라짐"을 인지할 경로 자체가 없다. 반면 선착순의 손실(고득점 친구가 owner 화면에 영원히 안 뜸)은 owner가 매번 목격한다.

  밀려나 `+N`으로 접힌 친구도 자기를 찾을 수 있어야 하며, `+N` 배지 탭 → 섹션 4 리스트 스크롤 동선과 스킵 링크가 그 경로다(랜덤 배치 후에도 유지 확인됨). 전원 정보는 섹션 4 리스트(점수 내림차순)에 그대로 있으므로 정보 손실은 없다.
- **"방금 등록한 본인 별은 상한 밖이어도 항상 개별 렌더링"** 규칙은 유지한다(이제 "31번째 이후 등록자"가 그 케이스가 된다). 강조 방식(크기 왜곡 금지, outline/pulse/aria-label)은 아래 "본인 별 강조 방식" 절 그대로 적용.
- **기존 데이터 하위 호환**: 이미 원격 DB에 적용된 우주/별이 있을 수 있다. 위치 컬럼이 빈 기존 별의 백필 전략(마이그레이션 시점 일괄 산출 vs 조회 시 지연 산출)이 필요하며, 어느 쪽을 택하든 **백필 후에는 위치가 다시 변하지 않아야 한다.** 전략 선택은 CTO 소관.
- 애니메이션 위상(twinkle/float)의 seed 기반 결정론 규칙은 그대로 유지한다(아래 "애니메이션 위상" 절 참조 — `Math.random()` 금지 원칙은 위상에는 계속 적용된다. 이 변경은 **위치**에만 등록 시점 랜덤을 도입하는 것이다).

### 애니메이션 위상

`Math.random()` 금지. **친구 id 해시 기반 결정적 함수**로 twinkle/float delay를 산출한다(SSR/CSR hydration mismatch 방지 + 리렌더 시 위치·위상 고정). twinkle ~4.2초, float ~7.5초, 음수 delay로 위상을 어긋낸다.

### 배경

성운/별먼지는 이미지 에셋 없이 CSS `radial-gradient` 레이어로 구현한다(애니메이션 0개). 커스텀 일러스트는 Phase 3 이후(구현 단계 참조).

### 별 탭 동작 (Phase 1)

4번째 리스트의 해당 행으로 부드럽게 스크롤 + 1.2초 하이라이트 펄스. 바텀시트 팝업 + 재바이럴 CTA는 Phase 2.

### 접근성 (a11y)

- 4번째 리스트를 시각화의 **공식 접근성 대체 구조**로 지정한다 — `<ol>`로 순위/점수/등급(tier)/한줄평을 텍스트로 제공한다(별도 숨김 리스트를 이중으로 만들지 않는다).
- 각 별 `<button>`의 `aria-label` 포맷은 위 "tier 사용 방식 (확정)" 절의 확정 포맷(`"{name}, 궁합 점수 {score}점, {tier.labelKo}, 전체 {total}명 중 {rank}위"`, 본인 별은 `"(나) "` 접두)을 그대로 따른다. 점수 숫자만으로는 전달되지 않는 정성적 정보(tier)를 시각 외 채널로 보강하는 것이 목적이다.
- 시각화 앞에 "별 시각화 건너뛰고 궁합 순위 목록으로 이동" 스킵 링크를 필수로 둔다(별이 최대 31개 tab-stop이므로).
- 별 시각 원 크기와 무관하게 버튼 히트 영역은 `min-width/height: 44px`를 강제한다(시각 레이어는 `aria-hidden="true"`인 별도 `<span>`으로 분리하며, 시각 레이어와 그 위 장식(스파이크/플레어)은 `pointer-events: none`으로 이웃 별의 탭을 가로채지 않아야 한다 — 장식이 코어 박스 밖으로 삐져나가는 구조라 이웃 별의 클릭을 가로챌 수 있고, 별 31개가 붙어 있는 화면에서 실제 사용성 결함이 되기 때문이다).
- `prefers-reduced-motion: reduce`에서 모든 애니메이션을 제거한다.

### 대비

이름 라벨 텍스트는 별 밝기와 **완전히 분리**해 항상 흰색 고정 + `rgba(12,18,32,0.72)` 스크림 pill 배경을 사용한다. 낮은 점수 별이라도 이름은 항상 4.5:1 이상을 유지한다.

### 다국어/긴 이름

문자 수가 아닌 **폭 기준 말줄임**(`max-width: 56px` + ellipsis + nowrap, 줄바꿈 금지)을 사용한다. CJK/라틴 폭 차이 때문에 문자 수 규칙은 금지한다. 잘린 이름의 풀네임은 `aria-label`과 상세 뷰에 항상 보존한다. 소유자 별 라벨은 `max-width: 96px`.

### 반응형

페이지 컨테이너 `max-width: 480px` 전역 패턴을 따른다. 시각화 컨테이너 `width:100%; max-width:480px; aspect-ratio: 1/1.05`. 별 위치는 비율(%)로 저장·적용하고, 별 직경은 px 고정. 375~480px만 검증하면 된다(데스크톱 별도 레이아웃 불필요).

기존 다크 그라디언트 `linear-gradient(180deg, #0c1220 0%, #2e1431 100%)`와 `app/globals.css`의 기존 토큰만 사용하고, 신규 디자인 토큰은 생성하지 않는다.

nanoid, 알파벳 `23456789abcdefghjkmnpqrstuvwxyz`(혼동 문자 0/O/1/l/I 제외) 12자리, 약 59.6bit 엔트로피. 순차 ID 대비 열거 공격 불가능. `package.json`에 nanoid가 이미 의존성으로 존재(`app/api/face-spoiler/upload/route.ts`에서 선례 사용 중)하므로 신규 의존성 추가가 아니다.

### 소유권 증명 메커니즘

**Phase 1 결론: 필요 없음.** owner와 friend가 동일한 `/universe/{publicId}` 페이지를 보고 동일한 액션(친구 입력)만 가능하므로, Phase 1 기능 범위에는 "owner만 할 수 있는 동작"이 존재하지 않는다.

**Phase 2 이후 대비**: 마이그레이션에 이미 `owner_token_hash` 컬럼이 준비되어 있다. 우주 생성 시 서버가 원문 토큰을 발급해 **HttpOnly, Secure, SameSite=Lax 쿠키**로 브라우저에 심고, DB에는 해시만 저장한다. 이후 owner 전용 액션(예: 친구 별 삭제, 어뷰징 신고 처리)이 필요해지면 요청 쿠키의 원문 토큰을 해시해 `owner_token_hash`와 비교해 검증한다.

> **사용자 초안의 localStorage 방식과의 차이(권장 변경)**: 사용자 브리핑은 "localStorage에 owner secret 토큰 저장"을 예시로 들었으나, localStorage는 XSS에 취약하고 JS로 임의 접근 가능하다. 이미 마이그레이션 주석에도 HttpOnly 쿠키 전제로 컬럼이 설계되어 있으므로, **HttpOnly 쿠키 + 서버 검증**을 권장안으로 채택한다. localStorage는 채택하지 않는다.

### 개인정보: 친구 정보 공개 범위 — ✅ **확정 (2026-08-18 사용자 결정, B안 채택)**

**이름만 공개, 생년월일시는 비공개(계산에만 사용)**로 확정됐다(선택지 A/B/C 및 검토 배경은 "결정 이력" 절 참조).

- **API 응답에 생년월일/생시 관련 필드를 일절 포함하지 않는다.** `GET /api/universe/{publicId}`의 `guests[]`와 `POST /api/universe/{publicId}/guests`의 응답에 노출 가능한 필드는 `starSeed`, `name`, `score`, `tier`, `oneLinerId`, `oneLinerKo`, `confidence`뿐이다(아래 "API 설계" 절 참조 — 실제로 이 PRD의 API 스키마는 애초에 생년월일/생시를 응답에 넣지 않는 형태로 설계되어 있었으므로, 이번 결정으로 API 형태가 바뀐 것은 아니고 그 설계가 정책으로 공식 확정된 것이다).
- **owner도 예외가 아니다.** 친구는 "남의 링크"에 자기 생년월일시를 입력하는 것이고, 그 값이 링크 소유자에게 통째로 넘어간다고 기대하지 않는다. 링크를 아는 제3자든 owner든 동일하게 생년월일시는 비공개로 처리한다. *(이 owner 예외 없음 해석은 CPO가 내렸다 — 사용자 결정문에 owner 케이스가 별도로 언급되지 않아 가장 보수적인 방향으로 적용한 것이다.)*
- **DB에는 계산을 위해 그대로 저장하되, API 응답 경계 밖으로 나가지 않는다.** `universes`/`universe_guests`의 `birth_date`/`birth_time`/`birth_time_unknown`/`calendar_type`/`is_leap_month` 컬럼은 삭제하지 않는다(궁합 재계산·감사·매트릭스 버전 백필에 필요) — 응답 직렬화 단계에서 제외하는 것이지 스키마를 바꾸는 것이 아니다(아래 "스키마" 절 컬럼 비고에 표시).

### 어뷰징 방지

- **우주 생성 rate limit**: ✅ **확정 — IP당 일 5회**(운영 중 어뷰징 관측 데이터로 조정 전제, 근거는 "결정 이력" 절 참조). `creator_ip_hash` + `created_at` 인덱스로 최근 N시간 내 생성 건수를 서버에서 카운트. Vercel 서버리스 환경에서는 프로세스 메모리 기반 rate limit이 인스턴스마다 리셋되어 신뢰할 수 없으므로, **DB 카운트 쿼리 기반 슬라이딩 윈도우**로 구현한다(인메모리 캐시 방식 채택 안 함).
- **친구 등록 rate limit**: `universe_guests.creator_ip_hash` + `universe_id` 부분 인덱스로 동일 IP가 짧은 시간 내 여러 우주에 반복 등록하는 패턴을 탐지/차단.
- **우주당 참여 인원 하드 캡**: ✅ **확정 — 300명**(근거 없는 추정치로 시작해 운영 중 조정 전제, 근거는 "결정 이력" 절 참조). 3번째 영역의 "개별 렌더링 상한 30명"은 **시각화 표시 상한**이지 참여 상한이 아니다(31명 이상은 +N 배지로 계속 수용). 300명 초과 시 신규 등록을 거부하고 `UNIVERSE_FULL` 에러(아래 "에러 처리" 절)를 반환한다.
- **동일인 재등록**: E1 정책(업서트)이 1차 방어. 동일인이 이름을 바꿔 여러 번 등록하는 것까지는 막지 않으며, 이는 IP 쿨다운으로 완화한다(완전 차단은 불가능 — 로그인이 없는 기능의 근본적 한계로 인지하고 넘어간다).
- **Phase 2 검토**: 어뷰징이 실제로 관측되면 CAPTCHA/Turnstile 등 봇 방지 도입 검토(Phase 1에는 포함하지 않음 — 무료 바이럴 기능의 진입장벽을 스스로 높이는 트레이드오프가 있으므로 데이터 없이 선제 도입하지 않는다).

## 자미두수 매트릭스 연동 인터페이스

### PRD가 요구하는 계약 조건 (필수)

- 점수는 **정수**이며, 실사용 값은 하한/상한으로 클램프된다(현재 구현 기준 12~99 — 아래 "구현 현황"과 "점수 범위" 참조). **이론적 정의역(0~100)과 실사용 분포가 다르다**는 점을 계약 조건에 명시한다 — UI/디자인이 점수 범위를 가정할 때는 반드시 실사용 클램프 값을 정의역으로 삼아야 하며, 0과 100은 구조적으로 나오지 않는다.
- 점수와 별개로 **등급(tier)**을 함께 반환해야 한다. tier는 점수를 6단계 구간으로 나눈 슬러그+한국어 라벨이며, 접근성 요구사항(궁합 순위를 시각 정보 외 채널로 전달)을 충족시키는 핵심 텍스트 채널로 쓰인다(디자인 컨셉 절 a11y 참조). 단순 내부 값이 아니라 4번째 리스트와 별 `aria-label`에 노출되는 사용자향 텍스트다.
- 한줄평은 **표시 영역 제약 내**(3번째 시각화 강조 라벨은 짧게, 4번째 리스트는 조금 더 길게 허용 — 정확한 글자 수 상한은 designer 협의 필요, 이 PRD에서는 "카드/리스트 레이아웃이 깨지지 않는 길이"로 정의)
- 조회는 **동기 함수**, 외부 API 호출 없이 **결정론적**(동일 입력 → 항상 동일 출력)
- 점수 산출 근거(factor breakdown)를 함께 반환해 "왜 이 점수인지" 최소한의 설명력을 제공
- 매트릭스 버전을 결과에 함께 반환해 스냅샷 재현성을 보장

### 구현 현황 (2026-08-18 기준 — 위 계약을 충족)

```typescript
// libs/zi-wei-dou-shu/calculators/friend-compatibility.ts
export const calculateFriendCompatibility = (
  owner: FriendCompatibilityPerson,
  guest: FriendCompatibilityPerson
): FriendCompatibilityResult => { /* ... */ };

interface FriendCompatibilityResult {
  score: number;        // 정수. 실사용 범위 12~99 (아래 "점수 범위" 참조, 0/100은 미도달)
  tier: string;         // 등급 슬러그 (6단계, 아래 "등급(tier) 체계" 참조)
  oneLinerId: string;   // 한줄평 템플릿 ID (i18n 키)
  oneLinerKo: string;   // 한국어 한줄평 원문

  matrixVersion: string; // 예: "fu-1.0.0"
}
```

LLM/네트워크 호출 없음, 순수 함수, 대칭성(`calculate(A,B) === calculate(B,A)`) 검증됨. 매트릭스는 유파 삼합파(三合派) 기준 6개 축(띠/오행국/명궁 자리/타고난 성향/친구 자리/사화 교차/천간)으로 구성되어 있다.

> **확정 예정 필드 (아직 코드 미반영)**: 위 인터페이스는 이 PRD 작성 시점의 실제 코드다. 여기에 `confidence: "exact" | "estimated"`와 `chartCombinations: number`(평균한 명반 조합 수 — owner만 미상 12 / 양쪽 미상 144 / 양쪽 확정 1) 필드가 추가될 예정이다 — 자세한 배경과 요구사항은 아래 "(b) 태어난 시간을 모르는 사용자 처리" 절 참조.

### 점수 범위 (⚠️ 0~100 아님 — 실사용 12~99)

`friend-compatibility-table.ts` 기준 실제 상수:

| 상수 | 값 | 의미 |
|---|---|---|
| `FRIEND_COMPATIBILITY_BASE_SCORE` | 58 | 기준점. 전 조합(2,256쌍) 시뮬레이션 중앙값이 64~68에 오도록 튜닝됨 |
| `FRIEND_COMPATIBILITY_SPREAD` | 1.0 | 각 축 원(raw) 기여도에 곱하는 확산 계수 (중앙 과밀 완화용 튜닝 노브) |
| `FRIEND_COMPATIBILITY_MIN_SCORE` | 12 | 노출 점수 하한 (clamp) |
| `FRIEND_COMPATIBILITY_MAX_SCORE` | 99 | 노출 점수 상한 (clamp) |

즉 **실사용 점수는 12~99 구간에만 존재하고 기준점 58 근처에 몰린다.** DB 컬럼(`universe_guests.score SMALLINT CHECK (score BETWEEN 0 AND 100)`)의 `0~100` 제약은 이론적 여유를 둔 것일 뿐 실제로 0이나 100이 저장되는 경우는 구조적으로 없다. **UI/디자인에서 점수를 시각적으로 매핑할 때는 이 실사용 범위(12~99)를 정의역으로 삼아야 하며, 0~100 기준 매핑은 실사용 구간에서 변별력을 잃는다**(디자인 컨셉 절의 "점수 → 시각 매핑 (확정)" 참조 — 이 문제로 재보정이 트리거됐고, 정의역을 12~99로 잡는 것으로 확정됐다).

**점수 분포 튜닝하지 않음 (확정, 2026-08-18 CTO 협의)**

하한을 올려 저점 구간을 압축하는 식의 튜닝은 **하지 않는 것으로 확정**했다. 근거:

1. 점수를 위로 압축하면 정의역 `[12, 99]` 기준으로 이미 재보정을 마친 별 크기/밝기 매핑(디자인 컨셉 절 참조)이 다시 변별력을 잃는다 — 이 기능의 유일한 시각적 서사가 죽는다.
2. 대비가 곧 공유 동기다. 전부 무난한 점수만 나오면 스크린샷을 찍어 공유할 이유가 없어진다(바이럴 목적과 정면으로 배치).

대신 **카피 요구사항**으로 대응한다: 하위 2개 등급(`distant-star`, `crossing-comet`, 합계 26.0%)의 한줄평은 "안 맞는 사람"이 아니라 **"궤도가 다른 사람"** 톤으로 읽혀야 한다. 낮은 점수를 관계의 실패가 아니라 서로 다른 결의 흥미로운 차이로 프레이밍하는 것이 목적이다(현재 growth-strategist 카피 검수 중, 확정 카피는 `FRIEND_ONE_LINERS`의 `fu-distant-*`/`fu-crossing-*` 계열 항목에 반영).

### 자형(自刑) 페널티 유지 (확정, 2026-08-18 CTO 협의)

진(辰)·오(午)·유(酉)·해(亥)띠끼리는 같은 띠라도 "자형(自刑)"에 해당해 `punishment` 관계(-13)가 적용된다(`ZODIAC_RELATION_DELTA.punishment`, `libs/zi-wei-dou-shu/calculators/compatibility.ts`의 `isPunishment`/자형 판정 로직 — 이 판정은 기존 유료 1:1 궁합과 공유하는 로직이다). 일반적인 "같은 띠"는 `same-sign`(+7)로 우대받는데, 이 네 띠만 예외적으로 페널티를 받는 구조라 "같은 띠 친구인데 왜 점수가 낮지?"라는 반발 우려가 제기됐다.

**완화하지 않고 이론 정확도를 유지하는 것으로 확정했다.** 근거:

1. 실제 노출 빈도가 낮다 — 같은 띠일 확률(1/12) × 자형 대상 띠일 확률(4/12) ≈ **전체 쌍의 약 2.8%**. 소수 케이스 때문에 전체 매트릭스의 이론적 근거를 깎을 이유가 없다.
2. 반발이 무서워 이론값을 낮추는 것은 "근거 기반 콘텐츠"라는 브랜드 원칙(`.claude/rules/brand-voice.md`, `content-guidelines.md`)에 반한다 — 감으로 점수를 조정하는 것과 다르지 않다.

**요구사항**: 자형이 적용되는 한줄평은 단순히 낮은 점수를 통보하는 톤이 아니라, **왜 같은 띠인데도 그런지 이유를 설명하는 톤**을 유지해야 한다(자형 개념 자체를 노출하지 않되 "같은 에너지끼리 부딪히는 패턴"이라는 근거는 전달). 자형은 `punishment` 축(zodiac relation)에서 발생하고 한줄평 ID는 `punishment`×오행 관계(생/비화/극)로 조합되므로(`fu-{zodiac}-{element}` 규칙), **자형 케이스가 실제로 매핑될 수 있는 한줄평은 `fu-punishment-generate`/`fu-punishment-same`/`fu-punishment-overcome` 3종 전부**다(두 사람이 같은 자형 띠여도 오행국은 서로 다를 수 있으므로 세 조합 모두 발생 가능 — CPO 메시지의 `fu-punishment-same` 단건 지목은 대표 예시로 이해하고 범위를 넓혔다). 3종 모두 같은 설명 톤 원칙을 적용해야 한다. 카피 최종 검수는 growth-strategist 영역.

### 등급(tier) 체계

점수를 6단계로 나눈 구간 등급이며, 접근성 요구사항(시각 정보 외 채널로 궁합 순위를 전달)을 충족하는 핵심 텍스트다. 4번째 리스트의 각 행과 별 `aria-label`에 노출한다(디자인 컨셉 절 a11y 참조).

| tier 슬러그 | 점수 구간 | 한국어 라벨 |
|---|---|---|
| `twin-star` | 90~100 | 쌍성 |
| `bright-orbit` | 78~89 | 밝은 궤도 |
| `warm-gravity` | 66~77 | 따뜻한 인력 |
| `steady-orbit` | 54~65 | 안정 궤도 |
| `crossing-comet` | 42~53 | 스치는 혜성 |
| `distant-star` | 0~41 | 먼 별 |

구간 자체는 0~100을 빈틈없이 덮도록 정의되어 있지만(위 "점수 범위" 절 참조), 실사용 점수가 12~99이므로 실질적으로 `distant-star`는 12~41, `twin-star`는 90~99 구간에서만 관측된다. EN/JA 라벨은 아직 정의되지 않았으며(아래 "(c) i18n 출시 정책" 절과 동일하게 Phase 1은 KO만), Phase 2 이후 `oneLinerId`와 동일한 방식으로 `tier` 슬러그를 키로 하는 다국어 사전을 추가한다.

### owner 한줄평 테이블 (신규 계약, 2026-08-19 CPO 결정)

섹션 1(owner 요약)에 신설되는 owner 운세 한줄평의 계산 계약이다. 위 "화면 구성 > 1. 최상단 — owner 요약" 절의 제품 요구사항을 계약 조건으로 정리한 것이며, 축 설계 자체는 ziwei-expert 산출물이다.

**친구 궁합 매트릭스(`FRIEND_ONE_LINERS`/`calculateFriendCompatibility`)와의 관계**: 완전히 별도의 테이블/함수다. 상대가 없는 1인 차트라 판정 축 자체가 다르고(예: 명궁 주성, 신궁, 오행국 등 1인 차트만으로 도출되는 축 — 구체 축 선정은 ziwei-expert 소관), 반환 형태도 다르다(owner 한줄평은 `factors`(근거 breakdown) 없이 슬러그+문구만 반환한다 — 상대가 없어 "왜 이 점수인지" 비교 근거를 만들 필요가 없다).

**계약 조건**

| 항목 | 요구사항 |
|---|---|
| 입력 | owner 1인 명반(생년월일시). `estimated`(시간 미상)인 경우 시간 의존 축을 제외한 폴백 조합 사용. 친구 데이터 의존 없음 |
| 산출 방식 | 결정론적 조회, LLM 호출 없음, 동일 입력 → 항상 동일 출력 |
| 날짜 의존 | 금지 — 조회 시점(오늘 날짜)과 무관하게 항상 같은 결과 (불변, 공유/스크린샷 유통 특성상 필수) |
| 결과 가짓수 | 최소 50가지 이상 |
| 문구 길이 | 45자 이내 |
| 어투 | 존댓말 |
| 전문 용어 노출 | 문구 표면에 자미두수 전문 용어 노출 금지 |
| 금지 표현 | 의료/법률/투자 조언으로 오해되는 표현, 적중률 주장 |
| 반환 형태 | `{ ownerOneLinerId: string, ownerOneLinerKo: string }` — 슬러그만 저장, 문구는 조회 시점에 사전에서 해석(`libs/universe/one-liner.ts`의 append-only 슬러그 패턴과 동일 — `resolveOneLinerKo`에 대응하는 owner 전용 resolver 필요) |
| estimated 폴백 | 시간 미상이어도 산출 가능한 축 조합 필요. 이 경우에도 별도 고지 문구를 한줄평에 덧붙이지 않는다(이미 estimated 배너로 1회 고지됨) |
| 개인정보 | 원본 생년월일시/명반 구조 응답에 미노출(`PersonalDataKey` 가드), 문구가 생시를 특정 가능하게 서술 금지(예: "새벽에 태어난 분들은…" 류 금지) |

**tier 체계와의 차이**: 친구 궁합의 `tier`(6단계, 점수 구간)는 이 owner 한줄평에 적용되지 않는다. owner 한줄평은 점수/등급 없이 문구 하나만 반환한다 — 섹션 5(다른 운세 홍보)로 이어지는 "티저" 역할이므로 점수화된 진단으로 오인되면 유료 상품(평생운세 등)을 무료 화면이 잠식하게 된다.

**API/스키마 반영**: 아래 "API 설계" 절과 "데이터 요구사항 > 스키마" 절에 필드 추가를 반영했다. 산출 시점(우주 생성 시 저장 vs 조회 시 지연 계산)의 최종 기술 판단은 CTO 소관이다(위 "1. 최상단 — owner 요약" 절 참조).

### 초기 확인 이슈 3건 (전부 해결/확정 완료)

#### (a) 성별 의존성 충돌 — ✅ **해결됨 (구현으로 확인)**

우려: 자미두수 대운 등은 성별에 의존하는데 friend 입력에는 성별이 없다.

확인 결과: `calculateFriendCompatibility`는 명반 생성 시 고정 플레이스홀더 성별(`male`)을 사용하고, 대운/유년 순역행 등 성별 의존 로직을 **일절 사용하지 않는다**(코드 주석에 명시, `male`/`female` 동치성 테스트로 검증 언급됨). 따라서 friend에게 성별을 받지 않는다는 컨셉 확정 사항과 충돌하지 않는다. 추가 조치 불필요.

#### (b) 태어난 시간을 모르는 사용자 처리 — ✅ **확정 (2026-08-18 CTO 확정, 미결 사항에서 결정으로 승격)**

우려: 시간 필수 vs "모름" 옵션 처리 방식. `calculateFriendCompatibility`가 받는 `FriendCompatibilityPerson.birthTime`은 **필수** `TimeBranchValue`이며(DB 스키마의 `birth_time_unknown`과 달리 함수 내부에 대체 처리가 없어 빈 값이면 `ZiWeiError`를 던짐), 이 갭에 대해 CTO가 아래로 확정했다.

**확정: 시진 전수 열거 + 평균 (PRD가 이전에 권장했던 1안·2안 모두 폐기)**

시간을 모르면 가능한 시진 12개를 전부 계산해 평균을 낸다(양쪽 다 모르면 12×12=144조합 평균). 전통 명리 실무의 정시법(定時法)을 자동화한 근사다.

**PRD가 권장했던 1안(시간 축 제외 후 재계산)은 폐기됐다.** 자미두수는 명궁이 확정돼야 나머지가 전개되는 구조라, 시진을 빼면 6개 판정축 중 5개(오행국까지 포함 — 오행국도 명궁에 의존)가 무너진다. CTO 실측 비교:

| | 정상(시간 앎) | 1안(시간축 제외, 폐기됨) | 확정안(전수 평균) |
|---|---|---|---|
| 서로 다른 점수 종류 | 79종 | 16종 | 59종 |
| 점수+한줄평 조합 종류 | 462종 | 17종 | 302종 |
| 최빈 점수 집중도 | 3.0% | 58점에 32.3% 집중 | 4.6% |

1안은 3명 중 1명이 정확히 58점을 받는다 — 친구들끼리 결과를 비교하는 게 핵심 재미인 기능에서 성립하지 않는다. 2안(대표 시진 정오 등 기본값 대입)은 틀린 명궁이 틀린 주성으로 연쇄돼 **틀린 값을 확신 있게 제시**하게 되므로 배제됐다(전수 평균은 "모른다"는 사실 자체를 계산에 반영하지만, 기본값 대입은 "안다"고 거짓 전제하는 차이).

**요구사항 반영**

1. **`confidence: "exact" | "estimated"` 필드**가 결과에 포함된다. ✅ **쌍(pair) 단위 계산으로 확정** (2026-08-18 CTO 실측 확인 — 앞서 "재확인 중"이라 달아둔 전제는 해소됐다). owner만 시간 미상이면 `chartCombinations: 12`, 양쪽 다 미상이면 `144`, 양쪽 다 확정이면 `1`이다. `chartCombinations` 필드도 API 응답과 타입 정의에 함께 반영한다(아래 "API 설계" 절 참조).
2. **시간 미상이면 최고 등급 `twin-star`가 나오지 않는다(도달률 0%).** 평균화가 분포 꼬리를 깎기 때문이며, 이를 인위적으로 되살리지 않기로 확정했다 — 근거 없이 불확실성을 증폭하면 결정론적 엔진 자체의 신뢰를 스스로 훼손하기 때문이다.
3. **owner 시간 미상은 우주 전체에 파급된다 (CPO 결정).** 모든 쌍에 owner가 포함되므로, owner가 시간을 모르면 guest가 시간을 알아도 그 우주의 모든 결과가 `estimated`가 되고 아무도 `twin-star`를 받을 수 없다. 별 크기/밝기 변별력도 함께 압축된다. 따라서 owner와 guest의 입력 폼을 다르게 취급한다.
   - **owner 생성 폼**: "시간 모름"을 무마찰 기본 옵션으로 두지 않는다. 체크 전에 "시간을 넣으면 친구들 결과가 더 뚜렷하게 갈려요" 수준의 안내를 먼저 노출하고, 그래도 모르면 진행시킨다(차단하지 않음). owner는 한 번만 입력하면 되고 진입 동기가 이미 강하므로, 약간의 마찰이 결과 품질 이득으로 상쇄된다는 판단이다.
   - **guest 입력 폼**: 마찰 최소화를 유지한다(위 안내 문구를 추가하지 않음). 처음 보는 링크에 생년월일을 넣는 순간이 바이럴 루프에서 가장 얇은 지점이라, 여기서 시간을 강요하면 루프가 끊긴다.
4. **별 크기 매핑 정의역은 우주마다 바꾸지 않는다 (CPO 결정).** `estimated` 우주는 점수 폭이 좁지만, 정의역을 우주별로 좁히면 같은 70점이 우주마다 다른 크기로 보여 사용자 간 스크린샷 비교가 깨진다. 디자인 컨셉 절의 `[12, 99]` 고정 정의역은 `confidence` 값과 무관하게 항상 동일하게 적용한다(해당 절에 교차 참조 명시).
5. **`estimated` 상태 UI 문구는 설명형으로 고정한다.** "정확도가 떨어집니다" 같은 부정형은 금지하되, Phase 1에는 owner가 시간을 재입력할 경로 자체가 없으므로("소유권 증명 메커니즘" 절 참조 — owner 토큰 검증은 Phase 2) "넣으면 더 선명해져요" 같은 행동 유도형 카피도 Phase 1에서는 쓰지 않는다(넣을 방법이 없는데 유도하면 막다른 배너가 된다). 노출 위치·확정 카피·aria-label 규칙은 디자인 컨셉 절의 `` `estimated` 상태 표시 (확정) `` 참조.

#### (c) i18n 출시 정책 — ✅ **확정 (2026-08-18 CPO/CTO 협의, 미결 사항에서 결정으로 승격)**

한줄평 24키 + 등급 6키 + factor 약 30종의 EN/JA 번역이 미착수 상태이고, `calculateFriendCompatibility`는 현재 EN/JA 로케일에서도 `oneLinerKo`(한국어)를 그대로 반환한다(`FriendCompatibilityResult`가 `oneLinerKo` 단일 언어 필드만 가짐 — 코드 확인됨). 이를 전제로 아래 정책을 확정했다.

- **홈 화면 신규 카드(`FriendUniverseCard`)는 KO 로케일에서만 노출한다.** EN/JA 사용자가 홈에서 이 기능을 발견해 들어갔다가 한국어 콘텐츠를 마주하는 경로 자체를 차단하는 것이 목적. `useLocale()` 등으로 로케일 분기해 EN/JA에서는 카드를 렌더링하지 않는다(다른 4개 카드는 기존과 동일하게 3개 언어 모두 노출).
- **`/universe/{publicId}` 링크 직접 진입은 로케일과 무관하게 항상 정상 동작한다.** KO 사용자가 공유한 링크를 EN 로케일 브라우저가 열었을 때 절대 차단하지 않는다 — 막으면 바이럴 루프(친구가 링크로 들어와 참여하는 것) 자체가 끊긴다. 이 경우 UI 골격(버튼/라벨/에러 메시지)은 브라우저 로케일에 맞춰 EN/JA로 노출하고, 한줄평·등급(tier) 라벨만 KO 그대로 노출하며 그 옆에 "이 결과는 한국어로 제공됩니다" 류의 짧은 안내 문구를 덧붙인다(문구 3개 언어 번역은 필요 — 안내 문구 자체는 UI 골격이므로).
- **EN/JA 한줄평·등급 라벨 번역은 Phase 2.** `oneLinerId`(템플릿 ID)와 `tier`(슬러그)가 이미 안정적인 계약으로 확정되어 있으므로(구조적으로 확장 준비됨), Phase 2에서는 이 슬러그들을 키로 하는 번역 사전만 얹으면 되고 계산 엔진/스키마 변경이 필요 없다.

UI 골격 텍스트(버튼/라벨/에러)는 Phase 1부터 3개 언어 모두 필요하다는 원칙(비기능 요구사항 절 참조)은 유지되며, 예외는 "한줄평/등급 라벨의 내용" 그 자체뿐이다.

## API 설계

| 엔드포인트 | 메서드 | 설명 | 인증 | 요청 | 응답 |
|---|---|---|---|---|---|
| `/api/universe` | POST | owner 우주 생성 | 없음(익명) | `{ birthDate, birthTime?, birthTimeUnknown, calendarType, isLeapMonth, gender, ownerName? }` | `{ publicId }` (owner 토큰은 Set-Cookie로 전달, 응답 바디에 포함 안 함) |
| `/api/universe/{publicId}` | GET | 우주 상세 + 친구 목록 조회 | 없음(익명, `publicId` 소지가 사실상 접근권) | - | `{ ownerSummary, guests: [{ starSeed, name, score, tier, oneLinerId, oneLinerKo, confidence, chartCombinations, placement }], guestCount }` |
| `/api/universe/{publicId}/guests` | POST | 친구 별 등록(궁합 계산) | 없음(익명) | `{ name, birthDate, birthTime?, birthTimeUnknown, calendarType, isLeapMonth }` | `{ starSeed, score, tier, oneLinerId, oneLinerKo, factors, confidence, chartCombinations, placement, isDuplicate }` |

> `confidence: "exact" | "estimated"` — owner 또는 guest 중 하나라도 시간 미상이면 `"estimated"`("(b) 태어난 시간을 모르는 사용자 처리" 절 참조). ✅ 쌍(pair) 단위 계산으로 확정(CTO 실측 확인).
>
> `chartCombinations: number` — 이 결과를 낼 때 평균한 명반 조합 수. owner만 미상이면 `12`, 양쪽 다 미상이면 `144`, 양쪽 다 확정이면 `1`.
>
> `placement: { angle, radiusRatio }`(또는 `{ xRatio, yRatio }`) — ⚠️ **신규 (2026-08-19 CPO 결정).** 등록 시점에 랜덤 산출 후 영구 저장된 별 위치를 비율로 반환한다. 절대 px가 아니다("화면 구성 > 디자인 컨셉(우주 시각화) > 배치" 절 참조). 필드 형태(극좌표/직교좌표)는 CTO가 최종 확정한다.
>
> `ownerSummary: { ownerName?: string, guestCount: number, ownerOneLinerId: string, ownerOneLinerKo: string }` — ⚠️ **`ownerOneLinerId`/`ownerOneLinerKo` 신규 (2026-08-19 CPO 결정)**, owner 운세 한줄평("화면 구성 > 1. 최상단 — owner 요약", "자미두수 매트릭스 연동 인터페이스 > owner 한줄평 테이블" 절 참조). 개인정보 공개 범위 B안 확정에 따라 owner의 생년월일/생시도 응답에 포함하지 않는다(위 "개인정보" 절 참조). 위 필드들 외에 추가되는 것은 owner 요약용 파생 텍스트(예: 빈 상태 문구 키)뿐이며 원본 생년월일시는 어떤 형태로도 직렬화하지 않는다.

### 상태 관리

- **서버/클라이언트**: `/universe/{publicId}` 페이지는 초기 데이터를 서버에서 fetch(SSR 또는 Route Handler 선호출) 후 클라이언트에서 친구 등록 시 낙관적 업데이트. 시각화/폼 상호작용이 필요하므로 페이지 루트는 클라이언트 컴포넌트.
- **로컬 상태**: 폼 입력값, 제출 중 여부, 방금 등록한 본인 `starSeed`(하이라이트 트리거), 시각화 스킵/스크롤 타겟
- **서버 상태**: 우주 상세는 재방문 시마다 재조회(글로벌 캐시 불필요, 방문자 수가 적은 기능이므로 과설계 지양)

## 에러 처리

| 에러 상황 | 에러 코드 | 사용자 메시지 | 처리 방법 |
|---|---|---|---|
| 잘못된/존재하지 않는 `publicId` | `UNIVERSE_NOT_FOUND` | "존재하지 않는 우주예요." | 전용 에러 화면 + 홈 이동 CTA |
| 네트워크 오류 | `NETWORK_ERROR` | "네트워크 연결을 확인해주세요." | 재시도 버튼 |
| 입력값 검증 실패 | `VALIDATION_ERROR` | 필드별 인라인 메시지 | 폼 값 유지, 실패 필드 포커스 |
| 자미두수 계산 실패 | `CALCULATION_ERROR` | "입력값을 다시 확인해주세요." | 폼 값 유지, 재시도 안내 (근본 원인 은폐 금지 — 기본값 대입 금지) |
| Rate limit 초과 (우주 생성) | `RATE_LIMITED` | "잠시 후 다시 시도해주세요." | 일정 시간 후 재시도 안내 |
| 우주당 참여 인원 하드캡 초과 | `UNIVERSE_FULL` | "이 우주는 참여 인원이 가득 찼어요." | 등록 버튼 비활성 + 안내 문구 |
| 동일 조합 재등록 | (에러 아님) | "이미 참여한 별이에요!" | 기존 결과 재표시 + 본인 별 강조 (E1) |

> **매트릭스 폴백 절 불필요 (CPO 확인, 2026-08-18)**: 미정의 조합이 구조적으로 존재하지 않는다 — 한줄평 24개 전부 도달 가능하고, 등급 6구간은 0~100을 빈틈·중복 없이 덮는 것이 테스트로 고정되어 있다(`FRIEND_ONE_LINERS`/`FRIEND_COMPATIBILITY_TIERS`). 따라서 "미정의 조합 시 폴백" 같은 에러 케이스는 이 표에 두지 않는다.

| 우주 생성 → 공유 클릭 전환율 | 우주 생성 완료 유저 중 "공유 링크 복사"를 클릭한 비율 | 클릭 이벤트 / 생성 완료 이벤트 | 베이스라인 측정 후 설정 |
| 링크 방문자 → 별 추가 전환율 | `/universe/{publicId}` 방문자 중 친구 입력 폼을 제출 완료한 비율 | 폼 제출 성공 / 페이지뷰 (동일 우주 재방문 owner는 제외하는 필터링 방법 별도 정의 필요) | 베이스라인 측정 후 설정 |
| 우주당 평균 친구 수 | 활성 우주(친구 1명 이상)의 평균 `guest_count` | DB 집계 쿼리 | 베이스라인 측정 후 설정 |
| 친구 → 신규 우주 생성 전환율(바이럴 계수 K) | 친구로 참여한 유저가 이후 자기 우주를 생성한 비율 | 참여 시 발급되는 익명 세션/쿠키 식별자로 추적 (✅ **확정 — Phase 2에서 설계**, 근거는 "결정 이력" 절 참조) | 베이스라인 측정 후 설정. K≥1이면 자생적 바이럴 성립 |

> 바이럴 계수 측정을 위한 익명 방문자 추적(쿠키 기반) 설계는 Phase 1 범위에 포함하지 않기로 확정했다. Phase 1에서는 최소한 "친구로 참여 → 홈 카드 클릭"의 연결고리를 analytics 이벤트로만 남긴다.

  **문제**: 이름 라벨 겹침은 랜덤 배치 도입과 무관하게 **현행 링 배치에서 이미 발생 중**이다. CTO 실측 기준 ring1은 별 12개의 호 간격이 43.8px인데 라벨 폭은 68px이다. 라벨까지 겹치지 않게 배치할 수 있는 이론 상한이 12~20명이라, **개별 렌더링 상한 30명과 구조적으로 충돌**한다.

  **그래서 배치 알고리즘으로는 풀리지 않는다.** 위 "배치" 절의 최소 간격 판정을 별 직경 기준으로만 두는 이유가 이것이다 — 라벨 폭까지 판정에 넣으면 배치 가능 인원이 30명 상한 아래로 떨어진다. (CPO가 랜덤 배치 요구사항에 "라벨 폭도 반영"을 넣었다가 이 상충을 확인하고 철회한 항목이다.)

  **방향(미확정)**: "전부 노출"과 "전부 숨김"의 중간을 본다. 전부 숨기면 우주가 익명 점밭이 되어 "누가 내 우주에 있는지"라는 이 기능의 핵심 가치가 사라지고, 전부 노출은 물리적으로 불가능하다. 유력안은 **상위 소수만 라벨 상시 노출 + 나머지는 탭 시 노출**이다(스크린샷에서 실제로 읽히는 이름은 어차피 몇 개뿐이고, 고득점 친구 이름이 후크로 작동하는 것이 바이럴 목적에도 부합한다).

  **착수 시점**: 현재 라운드(별 형태 / 랜덤 배치 / owner 한줄평)가 사용자 확인을 통과한 뒤. 이번 라운드에 끼워 넣으면 범위가 두 배가 되고 원 요구가 지연된다.
