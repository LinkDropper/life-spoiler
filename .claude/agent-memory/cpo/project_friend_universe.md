**친구 우주 궁합**(`specs/friend-universe-compatibility.md`)은 인생스포의 첫 **완전 무료 바이럴 전용 기능**이다. 2026-08-18 기획 착수, 같은 날 PRD·디자인 컨셉 확정 및 **사용자 구현 승인 완료**. Phase 1 구현은 CTO 산하에서 진행.

**Why:** 목적이 매출이 아니라 신규 유입이다. 그래서 로그인·결제·엔타이틀먼트를 전부 뺐다. 사용자가 직접 확정해 재논의 대상이 아닌 제약이 4가지 있다 — (1) 기존 `app/compatibility/`(유료 1:1 리포트, 로그인+profiles+LLM 해석)와 **완전 별도 기능**이며 기존 유료 플로우/데이터모델을 건드리지 않는다, (2) 익명 링크 기반(로그인 불필요, 링크 ID가 우주를 식별), (3) 점수·한줄평은 **AI 실시간 생성 금지** — 자미두수 사전 정의 매트릭스에서 결정론적 조회, (4) 완전 무료.

**How to apply:**
- 이 기능에 유료화·로그인·LLM 해석을 얹자는 제안이 나오면 위 4개 제약과 충돌하는지 먼저 확인하고, 충돌하면 사용자에게 되묻는다. 임의로 뒤집지 않는다.
- 무료이므로 [[fortune-type-entitlement-constraint]]의 `fortune_type` 발급 규칙을 따르지 않는다. `fortunes` 계열 테이블이 아니라 별도 테이블(`universes` / `universe_guests`)을 쓴다 — 신규 무료 기능을 기획할 때 이 분리 패턴을 선례로 삼을 것.
- 화면 6개 영역의 **순서를 사용자가 직접 지정**했다(요약 → 친구 입력 폼 → 우주 시각화 → 궁합 리스트 → 타 운세 홍보 → 공유 링크 복사). 순서 변경은 사용자 승인 사항.
- 사전 정의 문구(한줄평 등)는 **개별로 검수하면 안 되고 나란히 놓고 봐야 한다.** 이 기능은 친구 여러 명의 한줄평이 한 리스트에 동시에 깔리는 UI라, 문구 하나하나는 멀쩡해도 종결 어미가 겹치면 템플릿을 돌린 티가 난다(실제로 24개 중 22개가 같은 어미로 끝나는 상태였다). 사전 정의 문구 세트를 검수할 때는 항상 "같은 화면에 몇 개가 동시에 보이는가"를 먼저 확인할 것.
- 점수와 한줄평이 **서로 다른 축으로 산출되면 불일치가 사용자에게 보인다.** `oneLinerId`는 띠×오행 2축, `score`는 6축으로 정해져서 "점수는 높은데 설명은 부정적"인 조합이 나올 수 있다. 결정론적 매트릭스를 설계할 때 점수와 텍스트의 산출 축이 같은지 반드시 확인할 것 — 스크린샷으로 공유되는 콘텐츠에서 이 불일치는 신뢰를 직접 깎는다.
- **친구가 입력한 생년월일시는 owner를 포함해 누구에게도 노출하지 않는다**(사용자가 B안으로 확정, 이름만 공개). 친구는 "남의 링크"에 자기 정보를 넣는 것이라 링크 주인에게 통째로 넘어간다고 기대하지 않는다는 것이 근거다. 익명 공개 기능을 추가로 기획할 때 같은 원칙을 기본값으로 삼을 것 — DB에는 계산용으로 저장하되 API 경계 밖으로 내보내지 않는다.
- **소유자 한 명의 입력 누락이 우주 전체를 저하시킨다.** 모든 쌍에 owner가 포함되므로 owner가 출생시간을 모르면 친구가 알든 말든 그 우주의 모든 결과가 추정치가 되고 최고 등급이 구조적으로 봉인된다. 그래서 owner 폼에만 마찰을 주고 guest 폼은 무마찰로 뒀다. **허브-스포크 구조의 기능에서는 허브 쪽 입력 품질이 전체 품질의 상한**이라는 일반 원칙으로 적용할 것.
- **행동을 유도하는 카피는 그 행동을 할 수단이 있을 때만 쓴다.** estimated 안내에 "시간을 넣으면 더 선명해져요"를 넣으려다, owner 재입력 경로가 Phase 2라 막다른 배너가 된다는 걸 뒤늦게 발견했다. Phase 1은 설명형으로만 가고 설득은 입력 수단이 있는 생성 시점으로 옮겼다. 유도 문구를 승인하기 전에 "지금 이 화면에서 그 행동이 가능한가"를 먼저 확인할 것.
- **PRD를 쓰는 동안 사용자 용어의 "이름"은 남고 "의미"가 미끄러진다.** 사용자는 "owner 운세 한줄평"을 요청했는데 PRD를 거치며 그 용어가 "친구 유입 유도 문구"로 바뀐 채 구현까지 나갔고, QA에서야 발견됐다(2026-08-19에 실제 owner 1인 운세 한줄평 신설로 정정). 사용자 원문에서 따온 용어는 PRD 확정 전에 **원문과 나란히 놓고 "지금 이 문장이 사용자가 말한 그것이 맞는가"를 대조**할 것. 특히 그 용어가 마케팅적으로 더 쓸모 있는 다른 의미를 가질 수 있을 때 미끄러지기 쉽다.
- **시각 인코딩 채널이 중복이면 그 채널은 안정성과 맞바꿀 수 있다.** 별 위치를 점수 순위에 묶었더니 새 친구가 들어올 때마다 기존 별들이 밀려나 "내 별이 어디 갔지"가 발생했다. 순위는 크기·밝기·리스트로 이미 3중 전달되고 있었으므로 위치 채널을 버리고 **등록 시점 랜덤 + 영구 저장**으로 바꿨다(2026-08-19 CPO 확정). 공유·재방문이 핵심인 기능에서는 **"이 시각 속성이 다른 사용자의 행동으로 바뀌는가"** 를 먼저 묻고, 바뀐다면 파생값이 아니라 저장값으로 만들 것.
- **되돌릴 수 없는 것만 게이트로 잡는다.** owner 한줄평 승인 때 "슬러그는 append-only로 굳지만 **문구 원문은 조회 시점 해석이라 출시 후에도 수정 가능**"이라는 구조를 확인하고, 슬러그 체계만 붙잡고 문구 미세 지적(별 셋의 3개 셀이 서로 가까움 등)은 비블로킹으로 넘겼다. 승인 게이트를 설계할 때 **"이 항목을 지금 안 잡으면 영영 못 고치는가"를 먼저 분리**할 것 — 안 그러면 고칠 수 있는 것 때문에 릴리스를 막게 된다.
- **사전 정의 문구 세트에서 한 축의 한 값을 "순화"하면 다른 축의 변별력이 통째로 사라질 수 있다.** owner 한줄평의 dark(어두운 밝기군) 14개 중 10개가 순화 과정에서 "겉으로 드러나지 않는 사람"이라는 단일 테마로 수렴해, 별 14종의 개성이 그 열에서만 무너졌다(전체의 1/3). 순화 방향을 "숨긴다"가 아니라 **"그 값의 고유 성질이 다른 결로 나타난다"**로 잡으면 해결된다. 매트릭스형 문구 세트를 검수할 때는 개별 셀이 아니라 **열/행 단위로 나란히 놓고 "이 축을 고정했을 때 다른 축이 여전히 구별되는가"**를 볼 것.
- **이 기능의 시각 QA는 로컬에서 테스트 데이터를 만들 수 없다.** `.env.local`의 `NEXT_PUBLIC_SUPABASE_URL`이 **운영 Supabase를 가리키고** 로컬 스택이 없어서, 우주를 하나 생성하면 운영 DB에 행이 남고 Discord 웹훅까지 실제 발송된다. 대신 **기존 우주를 조회(읽기 전용)하면 부작용이 0**이다. 리더가 QA용으로 만들어 둔 우주가 운영 DB에 3개 남아 있다 — `4sdu7kcscw8y`(친구 10명, owner "지민", **exact 경로**), `d4gte4my8czg`(친구 1명, owner "시간모름테스트", **estimated 경로** — 생시 미상 분기 확인용), `e44n7dvraf6e`. **셋 다 정식 출시 전 삭제 대상**이며, CTO가 준비한 owner 한줄평 슬러그 정리 쿼리(006) 실행 시 함께 지우는 방안이 논의됐다(2026-08-19). UI 검증이 필요하면 새로 만들지 말고 이 링크를 조회할 것 — exact/estimated 두 분기를 모두 커버한다.
- **경쟁사 레퍼런스의 구조를 이식할 때, "우리 엔진엔 그 축이 없다"는 판단을 코드 확인 전에 내리지 말 것.** 2026-08-19 섹션1 리디자인에서 "타입 헤드라인을 넣으려면 엔진에 타입 분류 축을 새로 추가해야 하는 큰 스코프"라는 전제로 논의가 시작됐는데, 실제로는 `oneLinerId` 슬러그(`oo-{별}-{밝기}-{페이스}`)가 **이미 그 축 자체였고 DB 저장·API 노출까지 끝나 있었다.** 진짜 비용은 엔진이 아니라 표시용 라벨 카피 24개와 검수였다. 결정론적 매트릭스 기능에서 "새 분류가 필요하다"는 요구가 나오면 **먼저 기존 슬러그 스키마가 그 분류를 이미 인코딩하고 있는지 확인**할 것 — 이 프로젝트의 매트릭스 슬러그는 대부분 축을 그대로 문자열에 담고 있다.

- 궁합 점수는 이론상 0~100이 아니라 실제로는 기준점 58에서 가감된 뒤 12~99로 clamp된다. **점수를 시각 요소(크기/밝기 등)에 매핑할 때 0~100을 정의역으로 잡으면 실사용 구간에서 변별력을 잃는다** — 반드시 실제 분포와 6단계 `tier` 경계값을 기준으로 정규화할 것. 기획 단계에서 실제로 한 번 어긋났던 지점이다.
