`libs/zi-wei-dou-shu/{constants/friend-compatibility-table.ts, calculators/friend-compatibility.ts}`로
구현된 무료 바이럴 기능 "친구 우주 궁합"에는 아래 3가지가 **협상 불가 제약**으로 확정되어 있다.

1. **LLM 호출 금지.** 점수·한줄평은 전부 TS 상수 매트릭스 + 규칙 엔진에서만 나온다.
   기존 유료 궁합(`libs/services/ai/compatibility-interpreter.ts`)과는 완전히 별개 경로다.
2. **성별 비의존.** guest는 성별을 입력하지 않는다 → 대운(`calculators/dayun.ts`)·유년 순역행 사용 금지.
   `generateZiweiChart`는 gender를 필수로 받지만 실제로 gender를 쓰는 곳은 dayun뿐이므로
   고정값 male을 넣고, 테스트에서 `jest.doMock("../core")`로 female 강제 주입해 동치성을 증명한다.
3. **점수 완전 대칭.** `calc(A,B).score === calc(B,A).score`, tier·oneLinerId·factors까지 동일.
4. **시간 미상은 임의 시진 대입이 아니라 12(또는 144)판 전수 기대값.** `birthTime: "unknown"`이면
   해당 인물의 명반 12개를 모두 세워 축별 원(raw) 기여도를 평균한다. 전통 정시법(定時法)의 자동화 근사다.
5. **슬러그 append-only.** `oneLinerId`·`tier`는 삭제·개명 금지 (DB에 ID만 저장하고 문구는 렌더 시 조회).
   **문구 수정은 `matrixVersion` bump 대상이 아니다** — 버전은 점수에만 걸린다.
6. **한줄평은 리스트로 나란히 깔린다.** 종결 어미가 한쪽으로 쏠리면 템플릿 티가 한눈에 드러난다.
   24개의 최빈 종결 형태를 40% 미만으로 유지하는 회귀 테스트가 걸려 있다.

**Why:** (1) 무료 기능이라 호출당 비용이 곧 손실이고 즉시 응답이 필요하다.
(2) guest 입력 항목을 최소화해야 전환율이 나온다.
(3) 링크 소유자와 친구가 서로 조회했을 때 점수가 다르면 신뢰가 깨져 공유가 끊긴다.
이론적으로도 삼합파의 관계 판정축(지지 삼합/육합/충/형/해/파, 명궁 자리, 주성 상성)은 무방향이며,
방향성이 있는 오행 생극·사화 비화(飛化)는 합혼에서 "관계 전체에 걸리는 긴장/윤활"로 읽으므로
양방향 합산으로 대칭화하는 것이 정당하다.
(4) **시진을 모르면 자미두수가 쓸 수 있는 정보가 년주(年柱) 쌍으로 붕괴한다.** 명궁=f(월,시진) →
오행국=f(년간,명궁) → 자미 위치=f(오행국,일) 체인이 전부 시진을 통과하므로, 월/일 정보가 궁 좌표로
변환되려면 반드시 시진이 필요하다. 년간/년지의 순함수인 성요(록존·양인·타라·천괴·천월·천마·홍란·천희)를
축으로 추가해도 정보량이 100% 중복이라 소용없다. 실측: 시진 의존 축을 제외하면 결과가 17종으로 줄고
3명 중 1명이 정확히 같은 점수를 받는다. 반면 12판 전수 평균은 월/일 정보를 되살린다
(같은 년주·다른 월일 → 59 vs 60으로 갈림).

**How to apply:** 이 기능에 새 축·격국·해석을 추가할 때 위 3가지를 먼저 확인한다.
방향성 있는 축을 새로 넣으면 반드시 양방향 계산 후 합산/평균해 대칭화하고,
동률 tie-break은 정렬 키를 정규화해(이름 sort, 고정 우선순위 배열) owner/guest 순서 무관하게 만든다.
`calculators/friend-compatibility.ts`는 `core.ts`에 의존하므로 `calculators/index.ts`에서
re-export하면 순환 참조가 된다 — 라이브러리 루트 `index.ts`에서만 export한다.
점수 매트릭스를 손대면 `FRIEND_COMPATIBILITY_MATRIX_VERSION`을 올려야 한다 (DB 스냅샷 키).

**점수와 한줄평은 원래 다른 것을 잰다.** `oneLinerId`는 (띠 × 오행) 2축 = "관계의 성질",
`score`는 6축 = "종합 궁합"이다. 구조적으로 독립이라 부조화가 걱정됐지만 2,256쌍 실측 결과
등급·극성이 반대로 가는 경우가 0.18%(4건, 전부 79~80점 × `fu-harm-generate`)뿐이고
극성별 평균 점수도 단조(부정 48.7 < 중립 60.9 < 긍정 81.4)라 구조를 유지하기로 했다.
같은 축에서 나오므로 상관이 자연히 생긴다 — 억지로 tier를 한줄평 선택에 넣을 필요가 없다.

**불확실성을 인위적으로 증폭하지 않는다.** 시간 미상이면 평균화 때문에 꼬리가 깎여 최상위 등급
도달률이 0%가 되는데, 이걸 확산 계수로 되살리자는 유혹이 있다. CTO와 합의해 거부했다 —
정보가 적을 때 극단 판정을 피하는 것이 옳고, 근거 없이 분산을 부풀리면 이 엔진의 존재 이유인
결정론적 신뢰성을 스스로 훼손한다. 대신 "태어난 시간을 넣으면 결과가 더 선명해져요"를
입력 유도 지렛대로 쓴다.

## 2026-08-19 fu-1.2.0 — 띠 `neutral` 버킷(최빈 슬롯) 세분화

대표가 "궁합 순위에서는 꼭 시작이 '특별히 부딪힐 일은 없는데'인가"라고 물었고, 팀 리드가
48샘플 1,128쌍 실측으로 확인한 결과 실제 편향이었다 — `resolveZodiacRelation`이 이름 붙은
특수 관계(삼합/육합/충/형/해/파/같은띠)가 아니면 전부 `neutral`로 떨어뜨려 전체의 약 42%가
`neutral`로 쏠렸고, `fu-neutral-generate` 하나가 24개 슬롯 중 최빈(약 17%)이었다.

**해법: 이미 점수에 반영 중이던 `palaceRelation`(명궁 자리, 5종)을 한줄평 선택에도
재사용해 `neutral` 버킷만 세분화했다.** `fu-neutral-{element}-{palace}` 15개 슬러그
추가(`buildNeutralOneLinerId`). 점수 계산식은 전혀 안 건드렸다 — 이미 계산해 두던 값을
"어디에 더 쓰느냐"만 바꾼 것이라 골든 회귀 6행의 score/tier가 완전히 그대로였다.
결과: 최대 단일 슬롯 점유율 16.8% → 11.0%(약 35% 상대적 감소).

**세분화 축 선택 — "독립 축이면 아무거나 된다"가 아니라 실측 분포로 골라야 한다.**
생년 천간 관계(`resolveStemRelation`, 3종)도 후보였지만 실측하니 그쪽은 `neutral`이
80~83%로 명궁 자리(63~66%)보다 더 쏠려 있어 기각했다. 후보 축이 여럿이면 "무관한 독립
축인가"만 보지 말고 반드시 각각 실측 분포를 뽑아 비교할 것 — [[owner-one-liner-engine]]의
"오행국은 연간 음양과 무관하다"는 기각 사례와 반대로, 여기선 두 축 다 통계적으로 유효했고
분포의 균등함으로 골랐다.

**append-only 구현 패턴: 옛 슬러그를 삭제하지 않고 "선택 로직만 분기"한다.**
`fu-neutral-generate/same/overcome` 3개는 테이블에 그대로 두고(이미 발급된 게스트
스냅샷이 가리킴), 계산기의 `oneLinerId = ...` 한 줄만 `zodiacRelation === "neutral"`일 때
새 함수로 분기했다. 새 게스트만 세분화된 슬러그를 받고, 옛 게스트는 그대로 옛 문구가
보인다 — 마이그레이션도 백필도 필요 없었다.

**테스트 갱신이 실제 작업량의 절반이었다.** 슬롯 개수가 바뀌면(24→39, 도달가능 24→36)
하드코딩된 개수 단언, `RELEASED_ONE_LINER_IDS`(append-only 가드), `ONE_LINER_POLARITY`
(점수↔문구 정합성 QA 가드, 키가 `FRIEND_ONE_LINERS`와 정확히 일치해야 함), 골든 회귀 표의
개별 `oneLinerId` 값까지 전부 따라 바뀐다. 어미/오프너 분포 테스트는 임계값이 비율 기반이라
자동으로 재계산되지만, **새로 추가한 15개를 전부 "~사이예요."+기본 "-요."로 성의 없이
써서 실제로 두 테스트를 깼다** — 새 항목을 추가할 때도 기존 항목과 마찬가지로 어미/오프너
다양성을 처음부터 설계해야지, "새로 늘어난 만큼 자동으로 다양해지겠지"라고 가정하면 안 된다.
