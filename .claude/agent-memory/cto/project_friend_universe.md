2026-08-19 기준 "친구 우주 궁합"은 **Phase 1 + QA 2차 구현 완료 / 미커밋** 상태다. `supabase/migrations/005_create_friend_universe.sql`과 `006_add_universe_star_placement_and_owner_one_liner.sql` **둘 다 원격에 적용 완료**(리더가 사용자 승인 후 직접 실행, 006은 owner 한줄평 슬러그가 `oo-1.1.0`으로 정리되기 전 시점에 적용됨). 커밋·푸시는 하지 않았다.

**006 적용 후 QA로 owner_one_liner_id가 기록된 더미 우주가 2개 있다** (`publicId`: `e44n7dvraf6e`, `4sdu7kcscw8y` — 로컬 dev 서버 API로 리더가 직접 생성한 테스트 우주, 실사용자 아님). 도입절 6종 유지가 최종 확정됐으므로(ziwei-expert 검증 완료, 오행국이 천간 음양에 구조적으로 무관함을 증명) 슬러그가 더 안 바뀔 예정이지만, 혹시 정리 쿼리(`UPDATE universes SET owner_one_liner_id = NULL, owner_one_liner_version = NULL`)를 실행할 계획이면 이 두 더미 행도 자연히 함께 정리된다.

**006 적용은 owner 한줄평 슬러그를 동결시킨다.** 006이 적용되면 `universes.owner_one_liner_id`에 값이 쌓이기 시작하고 그 시점부터 슬러그는 append-only가 된다. 실제로 CPO 검수 반영 과정에서 페이스 슬러그 체계가 통째로 바뀌었는데(`-early/-mid/-late` 3버킷 → 실제 오행국값 6종, `oo-1.0.0` → `oo-1.1.0`), 006이 이미 적용된 뒤였다면 계약을 깨야 했다. **슬러그 구조에 이견이 있으면 006 적용 전에 끝내야 한다.**

**How to apply:**
- 005는 적용됐으므로 직접 수정 창이 닫혔다. 006은 아직 미적용이라 수정 가능하다.
- 재개 시 `mcp__supabase__list_migrations`로 현재 상태를 먼저 확인한다. 006이 목록에 있으면 적용된 것이므로 007을 새로 만든다.

## 별 위치는 점수와 분리됐다 (되돌리지 말 것)

원래는 점수 내림차순 순위로 동심원 2링에 배치해 "1등이 owner와 가장 가깝다"가 시각 설계의 축이었다. 이제 **위치는 등록 시점 랜덤 산출 → DB 영구 저장**이고, 점수는 크기/밝기(`getStarVisual`)에만 남는다.

**Why:** 순위 파생 좌표라 새 친구가 높은 점수로 들어오면 기존 별이 링을 갈아타며 위치가 흔들렸다. 재방문자에게 "내 별이 어디 갔지"가 발생해 재공유 동기를 깎았다. CPO가 "거리는 순위의 중복 채널이었고 크기·밝기·순위 목록이 이미 3중으로 전달하므로 정보 손실 없음"으로 승인했다.

**How to apply:** 링 상수(`RING_RADIUS_RATIOS` 등)는 삭제됐다. 배치 로직을 만질 때 순위 기반으로 되돌리지 않는다.

## 자유 랜덤 배치는 N=30에서 안전하다 (실측)

375px 뷰포트(335×352px 캔버스) 기준 1000회 시뮬레이션에서 **N=30은 전원 최대 크기인 최악 케이스에서도 실패 0건**. 성공률이 무너지는 건 **N=48 부근**이고 이론 패킹 상한(RSA 포화 ~55)과 일치한다 — 알고리즘이 아니라 물리적 공간 한계다.

**How to apply:** 배치 관련 파라미터를 조정할 때 이 수치가 기준선이다. 48명 초과 우주에서는 간격을 단계적으로 완화해 최선 후보를 채택하며, **등록 자체는 절대 실패시키지 않는다**(리더 확정).

## 후속 과제: 이름 라벨 겹침 (미해결, 별도 트랙)

**라벨끼리의 겹침은 지금도 검사되지 않고 현재 배치에서 이미 발생 중이다.** 구 ring1은 별 12개가 반경 83.75px에 놓여 호 간격 43.8px인데 라벨 폭은 68px이었다. 라벨까지 겹치지 않게 배치할 수 있는 이론 상한은 **12~20개** 수준이라, 30명 우주에서 이름이 읽히게 만드는 건 배치 방식을 바꿔서 풀리는 문제가 아니다.

**Why:** 라벨 표시 정책 자체(항상 노출 → 탭 시 노출, 또는 축약)를 다시 설계해야 한다. 이건 CPO 영역의 결정이 필요하다.

**How to apply:** 위치 랜덤화 작업과 함께 처리하려 들지 말 것(리더가 범위 분리 승인). 겹침 회귀 테스트는 코어 원만 검사하므로 "테스트 통과 = 이름이 읽힌다"가 아니다.

## 시각 QA는 리더가 헤드리스 크롬으로 직접 수행했다 (2026-08-19)

CTO/fullstack 세션은 브라우저가 없어 못 했지만, 리더가 로컬 dev 서버 + API로 테스트 우주(친구 10~15명)를 만들고 macOS 설치된 Google Chrome을 `--headless=new --screenshot`으로 띄워 실제 렌더링을 확인했다. 헤더/owner 한줄평/랜덤 배치/리스트/섹션5·6 전부 정상 확인됨.

**이 과정에서 캐치라이트(안 C) 결함을 실측으로 발견하고 리더가 직접 고쳤다.** 원인: 캐치라이트 배치 반경(코어 중심 32~40%)은 카드 중심 기준인데, `.core`의 기본 배경 그라디언트 초점은 `35% 35%`(카드 중심이 아님)라서, 캐치라이트가 그라디언트 자체의 밝은 구역과 겹치는 각도(대략 좌상단 방향)에서는 "흰 위에 흰"으로 완전히 안 보였다 — 확대 스크린샷으로 확인(예: 도윤 별은 초기값으로 캐치라이트가 전혀 안 보였음). 배경 밝기와 무관하게 항상 보이도록 캐치라이트 자체에 옅은 vignette 링(흰 중심 → 어두운 보라 링 → 투명)을 추가해 해결. 최소 크기도 `0.36배` → `max(0.5배, 6px)`로 올렸다. 수정 후 재스크린샷으로 전 스타(가장 작은 별 포함) 캐치라이트 가시성 확인 완료.

**How to apply:** `components/universe/UniverseStar.module.css`의 `.core::before`를 캐치라이트 반경/그라디언트 초점 기준으로 다시 손댈 일이 있으면, 카드 중심(캐치라이트 배치 기준)과 코어 그라디언트 초점(35%,35%)이 다른 좌표계라는 점을 반드시 감안할 것 — 둘을 헷갈리면 이 버그가 재발한다.

## 재논의 불필요한 확정 사항

- 궁합 점수·한줄평은 **LLM 호출 없이** 사전 정의 매트릭스로 결정론적 산출(`fu-1.1.0`). 기존 유료 궁합(`app/compatibility/**`)과 완전 별도이며 그쪽은 건드리지 않는다.
- **시간 모름 → 시진 전수 열거 후 평균**(12 또는 144조합). 시간 축 단순 제외안은 결과가 17종으로 붕괴(3명 중 1명이 58점)해 폐기. 임의 대표 시진 대입안은 틀린 명궁을 만들어 폐기.
- `confidence`는 **쌍 단위**다 → owner가 시간을 모르면 우주 전체가 estimated. 그래서 마찰 안내는 owner 생성 폼에만 넣고 guest 폼은 무마찰로 둔다.
- 개인정보 **B안**: 이름만 공개, 생년월일시는 계산 전용. 방어선은 DB select 컬럼 화이트리스트 + DTO 컴파일 타임 가드 두 겹.
- RLS는 **anon/authenticated 전면 거부 + service role 전용**. 실제 anon 키로 `permission denied` 확인 완료.
- `creator_ip_hash`는 **HMAC 필수**(단순 SHA-256은 IPv4 전수 대입으로 가역). `UNIVERSE_IP_HASH_SECRET` 미설정 시 rate limit이 fail-open되므로 **프로덕션 주입 필수**.
- 점수 분포·자형 페널티는 **튜닝하지 않는다**(CPO 확정). 지표를 맞추려 카피를 고치는 것도 금지 — 순서가 거꾸로다.

## QA 가드는 임계값을 베이스라인 기준으로 잡는다

극성 불일치 가드를 처음에 2%로 뒀는데 실측이 0.18%라 11배 여유였다. 가드가 있다는 사실만 남고 아무것도 못 잡는 상태였고, CPO가 지적해 0.5%로 조였다.

**Why:** 임의의 라운드 넘버가 아니라 현재 실측값의 배수로 잡아야 가드가 실제로 문다.

**How to apply:** 임계값 옆에 "현재 실측 X% / 임계값 Y%"와 그 숫자를 고른 근거를 주석으로 남긴다. 비율 가드는 해상도가 거치니(1쌍=0.044%p) **0건이어야 하는 불변식**을 함께 둔다.

**주의(내가 틀렸던 것):** 극성 불일치 가드는 EN/JA 번역에 **반응하지 않는다**. 극성 표가 `oneLinerId`로 키잉되고 점수는 언어 독립이라 값이 안 움직인다. 반대로 종결 어미 가드는 한국어 어미 분류라 **EN/JA에서 무의미해진다** — 번역 시 KO 전용으로 유지하고 별도 지표를 설계해야 한다.

## 별도 트랙으로 분리한 것

`libs/supabase/types.ts`의 수동 타입이 실제 스키마보다 **테이블 11개 뒤처져** 있고, `interface` 선언이라 supabase-js의 `Record<string, unknown>` 제약을 못 만족해 **모든 테이블에서 `.from()`이 `never`로 추론**된다. 공식 생성 타입으로 교체하면 해소되지만 import 파일이 80개라 "스키마 타입 동기화" 별도 트랙으로 분리했다. 상세는 `.claude/agent-memory/fullstack/supabase_type_inference_broken.md`.
